# Decision: add `make issue-close` so the orchestrator can close an issue, and only that

Issue #119 (Heavy). The human approved this record in a comment on #119 (2026-11-03, 19:26Z), copied here from the issue body.

- **Decision:** Add `make issue-close N=<number> [REASON=completed|not-planned]`, backed by `agent-kit/scripts/issue-close.sh`. It closes exactly one issue and does nothing else (no edit, label, reopen, delete, comment). It refuses unless the issue's comments from the repository owner's account show the process was followed: for Standard, an open `approved` issue, a latest `QA:` PASS at or after the last `Engineer:` commit comment, and a Close-layout `Orchestrator:` comment; Heavy needs two QA PASS; Light needs the Light Definition of done in the comments; not-planned needs an `Orchestrator:` comment recording the human's approved backlog review. The orchestrator closes through this target only.
- **Reason:** `process.md` already makes the orchestrator the closer, but no sanctioned path existed, so the human clicked every close, after every QA PASS. A wrapper that reads the recorded evidence and can only close removes that step without giving the orchestrator a general `gh issue close`. It follows the existing wrapper pattern: fixed `gh` calls, fail closed, validation before any call, tests with a stub `gh`.
- **Alternatives:**
  - Keep the human clicking closes: safest, no new trust, but the manual step stays and the process text stays contradictory. Rejected by the human's 2026-11-03 choice.
  - Let the orchestrator run raw `gh issue close`: no checks, and it opens the full issue-write surface (the token can also edit and label, including `approved`). Rejected.
  - A GitHub workflow that closes on a signal comment: the close happens server side, but it adds a CI file and Actions permissions (a human-only `.github/` change), runs on a delay, and the signal comment is as forgeable as any comment. Kept as the stronger later option if comment forgery is a worry.
  - A read-only `ready-to-close` list: no new write power and the same checks, but the human still clicks. The checks are one function in the script so a later list can reuse them.
- **Trade-offs:**
  - All roles share the repository owner's account, so "from the owner's account" proves a comment came from this session's token, not which role wrote it. An agent that can post `QA: PASS` and a Close comment could satisfy every check itself. The wrapper stops mistakes and shortcuts, not a role set on bypassing the process. The human's review and the label rule remain the real control. Mitigations: the QA PASS commit named in the Close comment must appear in the QA comment, Heavy needs two PASS, and not-planned needs a human-approved line (still a text claim).
  - The script reads the recorded lines, not the facts: it cannot see that a merge commit exists, was pushed, or that the human approved a diff.
  - A comment edited after posting keeps its `createdAt`; the check reads the current text but orders by creation. Accepted.
  - More surface in a protected, live-running script set; each refusal rule is code to keep in step with `process.md`.
- **Token (recommendations in the record the human approved):** the existing sandbox token already allows `gh issue close`, so no token change is needed. The wrapper's checks are advisory, because the same token can still run `gh issue close` and `gh issue edit` directly; raw closes stay at ask. No follow-up for stronger role separation for now; revisit after ten uses of the wrapper. The human's comment approved the record without separate answers to these two questions, so they stand as the recommendations.
