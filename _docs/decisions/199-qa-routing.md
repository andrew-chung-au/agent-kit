# Decision: route failing findings by points computed from the issue's QA comments

Issue #199 (Heavy). The human approved this record with the groomed body (2026-11-22 grooming, D-199-1 to D-199-5 answered with option 1; `approved` label covering body sha256 `923feeff991914639b94f52077c2cb3610e16010dfd62f3703abeff18003e4e1`, Orchestrator Claim comment on #199, 2026-11-22). Copied here from the issue body's `## Decision record`.

- **Decision:** The verdict follows from the findings: a finding fails when it is in scope (or `QA_SCOPE_STRICT=no`) and at or above `QA_FAIL_AT`, and `check-format KIND=qa` checks the verdict and counts against settings read with `read_settings` at the issue level. A new read-only script, `route-findings.py` (`make route-findings N=<n>`), parses every owner `QA:` comment with `check-format.py`'s parser, builds chains from `Related:`, and prints each failing finding's points, rounds, route and guard. Ships leave the issue's scope, so `issue-close.sh` is unchanged.
- **Reason:** The rules interact (points, chains, guard, ship rule, re-check scope), and on #196 to #198 the human and orchestrator applied them by hand. One deterministic reader over data already on the issue makes the route checkable and repeatable, and reuses #198's parser and #197's settings reader.
- **Alternatives:** (1) The orchestrator counts points by hand, as on #198: no code, but the count is unchecked and was already missed. (2) QA writes a `Points:` field in each finding: one more field to check, and QA must still read the history to fill it. (3) A state file under `.scratch/`: lost at `make clean-scratch`. (4) A function in #200's `findings.py`: #200 hasn't landed; it can import this module later.
- **Trade-offs:** Points depend on QA reusing an id for a finding that still fails and setting `Related:` well; a wrong link changes the route, and the check catches only links to ids that don't exist. `check-format KIND=qa` now reads the conf and the dump, not only FILE, so it needs `make settings N=<n>` first. A shipped finding needs one more short QA run before close, until #218.
- **Evidence:** `_docs/planning/kit-1.11/workflow-review.md` sections 3.5, 4.0, 4.4 and 12; the #198 comments (QA FAIL at f974d41 with F-198-7 `Related: F-198-4`; the Engineer's fix-round-2 approach review; the Close comment); `_docs/records/findings/196.json`, `197.json`, `198.json`; `filed.md` grooming notes A and C; `agent-kit/scripts/issue-close.sh` (two PASS comments for Heavy).

Design note from the body: points are computed from the issue's own `QA:` comments, not stored anywhere, so a re-run gives the same route and the orchestrator keeps no state.
