# Decision: grade decision points with Impact and Effort, continue past choices within a budget of points, and keep them in an append-only ledger per issue

Copied here from the issue body's `## Decision record`.

- **Decision:** A decision point has an id, the kit's existing `Impact:` (how bad if the wrong answer stands) and `Effort:` (the rework if the answer changes), a kind and a mode (`stop` or `continue`). Effort converts to points 1, 2, 3 exactly as for findings, derived and never stored. Thirteen stop kinds always wait; the one continue kind, `choice`, is taken on its recommendation while the points of open continued points, counted over every issue, stay within `DECISION_BUDGET`. Points live in `_docs/records/decisions/<issue>.jsonl`, append-only, with three events (`open`, `answer`, `reworked`), validated and listed by `decisions.py` (`make decisions`), which the orchestrator runs before each Engineer and QA launch. The human answers per point (`approve`, `q<n>=<option>`, `reject`); an amended or rejected continue point becomes a rework item. Mechanical steps and the pre-flight list are not decision points. The message to the human's decision block gains `Effort:`, and a `Rollback:` line for a continued point only (its presence marks the point continued); its first line stays (the human's ruling on D-204-2, 2026-11-23).
- **Reason:** Per-issue files can't collide when two branches or lanes add points, and appending keeps what the agent did and what the human answered as a record, as the findings rulings do (#200). Counting the budget over every issue matches what it protects: the human's backlog of reversible choices, which outlives one issue on a branch project. Running the check at each launch turns "new work stops starting" into a gate the orchestrator already passes through (`make settings`). Reusing Impact and Effort keeps one grade vocabulary (`customizing.md`) and one points rule for findings and decisions, and the decision block then reads like the ship-or-fix block. Mechanical steps have no options to choose between, so counting them would spend the budget on nothing; the #200 run showed the real stops were gates.
- **Alternatives:** (1) `_docs/planning/decisions-pending.md`, one Markdown file edited in place (proposal 3.6): readable, but edits lose the history, a script must parse prose, and parallel lanes conflict. (2) One `_docs/records/decisions.jsonl`: one file to read, but two branches appending to it conflict. (3) Count the budget per issue: simpler, but points of a closed issue on an unmerged branch would stop counting. (4) Give the pre-flight list points so the budget covers it: its items are tool prompts and gates, not choices, so it would only fill the budget. (5) A separate weight scale 1 to 3 by blast radius (proposal 3.6): rejected by the human (2026-11-23) as duplicating Effort, a second word for the same kind of size. (6) A `Point: stop|continued` line in the message: rejected in favour of `Rollback:`, which says the same by its presence and also tells the human what an answer would undo. (7) A total in the `Needs you:` line as in proposal 5.4: changes the line every reader of the message matches.
- **Trade-offs:** The ledger is written by the agent; that the agent recorded only what the human said rests on the same rule as `Orchestrator: Ruling` comments, and append-only is a rule, checked at the human's diff review, not by the script. Effort and kind are the agent's judgement; an under-graded effort spends less of the budget than it should, and a stop kind logged as `choice` is caught by `make decisions` only if the kind is named honestly. `DECISION_BUDGET=3` limits what today waits, uncounted, until the end of an issue, so existing projects see more stops until they set the budget. Effort on a decision means the rework if the answer changes, not the size of the work done, so the doc says so where it defines the block.
