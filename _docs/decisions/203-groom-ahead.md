# Decision: the PM grooms up to GROOM_AHEAD issues ahead, in an order kept in the roadmap file, marked by an orchestrator-set prefix and re-checked by a diff

The human approved this record with the groomed body (2026-11-23 grooming, D-203-1 to D-203-3 answered with option 1; `approved` label covering body sha256 `cd608474fbe615bd533b714a3de2dfd4b66bacfeb41528f30a3ceaec6feb4dec`, Orchestrator Claim comment on #203, 2026-11-23). Copied here from the issue body's `## Decision record`.

- **Decision:** The agreed order is the ordered list of the planning roadmap file the docs index names, one entry per issue with its trigger, and every filed issue is added in the same session (D-203-1, option 1). The orchestrator, not the PM, sets the `[groomed]` title prefix once a valid `PM:` hash record matches the body, removes it when the body changes without one, and counts groomed-ahead issues by the hash match, never the title (D-203-2, option 1). The PM records `Groomed at: <sha>` in its grooming comment; before the Claim the orchestrator reads `git diff --stat <sha>..HEAD` for the issue's Files paths and has the PM re-check on an overlap (D-203-3, option 1). `GROOM_AHEAD=0` is today's rule. Neither the hash rule nor who approves changes; grooming note B's two paths are written down and their lines recorded on the issue.
- **Reason:** Grooming ahead lets the human label several issues in one sitting, but it breaks two things the one-at-a-time rule gave for free: the order was always the next issue, and the body was always fresh. A named order file and a hash-based count restore the first, and a diff the orchestrator already reads at the Claim restores the second, without a new script. The prefix is a human-facing hint, so nothing mechanical depends on it.
- **Alternatives:** (1) An `Order:` line on each issue (#209's `Needs:`): scattered, with no single view. (2) A GitHub milestone or board: labels and boards belong to the human, and are not readable offline. (3) The PM sets the prefix at grooming: fewer steps, but nothing checks the hash record exists. (4) No prefix: the human opens each issue to see its state. (5) No staleness check: an Engineer or QA finds the conflict, at the cost of a fix round or a QA FAIL. (6) A `make groom-stale` script: mechanical, but a new live script beyond this issue.
- **Trade-offs:** The order file is one more thing to keep current, and an issue filed outside it is never groomed (socboard's twelve), so the orchestrator must add it at filing. The staleness check catches an overlap only by path, not by meaning: a merged change elsewhere that matters to the body is missed, and the re-check costs a short PM launch. A stale `[groomed]` prefix can mislead a human skimming the list until the orchestrator removes it, though it can never count. Grooming ahead means the human reads several bodies in one sitting, a larger single review.
