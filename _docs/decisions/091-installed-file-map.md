# Decision: one installed-file map in the kit folder, read by one shared parser

Issue #91 (Heavy). **This record is a reconstruction, written on 2026-11-09.** The human approved the original record on 2026-11-03 (Orchestrator comment https://github.com/andrew-chung-au/agent-kit/issues/91#issuecomment-6613018258, "items 1 to 8, as written"). That text was a sandbox file (`.scratch/91-decision-record.md`) that was never committed, and it cannot be recovered. This file is rebuilt from the issue body, the PM's comment https://github.com/andrew-chung-au/agent-kit/issues/91#issuecomment-6612997657 (which names the eight items), the Orchestrator's approval, the build issues #113 to #118, and the code that shipped. Where it says what the code does, the code was read. **The human read this reconstruction and confirmed it as the record on 2026-11-09 (stated in the session, not in a hashed issue body).**

- **Decision:** The eight items, in the order the PM's comment lists them:
  1. **Map file and format.** One plain-text file, `agent-kit/installed-files.txt`, inside the kit folder. Each line is `<path inside the kit> | <install path> | <kind> | <allowed-to-differ>`. It is read as text and never sourced or run.
  2. **`repo` versus `human-machine` entries.** `repo` means installed inside the repository. `human-machine` means installed by the human on their own machine (the push check, at `~/.agent-hooks/pre-push` and in each clean clone's `.git/hooks/pre-push`). A `human-machine` install path is data only: no tool opens, stats or expands it. The human compares it from the clean clone with git only, never `make`.
  3. **Shared parser and refusal rules.** `agent-kit/scripts/kit-map.py` (`parse_map`, `scan_installed`) is the only reader; `kit-check`, `kit-compare` and the import tooling call it, so they cannot disagree. A malformed map refuses the whole read with exit 2 (a wrong number of fields, an unknown kind or rule, a duplicate install path, a control character or line break other than newline, a source path that is absolute, holds `..` or starts with `~`, and for a `repo` entry an install path that is absolute, holds `..`, resolves outside the repo, or goes through a symlink).
  4. **Allowed-to-differ.** One of `none`, `optional` (added by #170 for tool-layer files a project may not use), `markers` (lines between `agent-kit: local-begin` and `agent-kit: local-end`), or `prefix:<text>`. A difference inside what is allowed is reported `local, ignored`; any other difference is `drift`.
  5. **Read-only use by each tool.** `kit-check`, `kit-compare`, the forward import and the reverse import all read the map through the shared parser and write nothing. The reverse import writes only a feedback bundle under `.scratch/` (`kit-feedback`). No tool copies an installed file; the human does, from a clean clone.
  6. **Release zip.** The map ships inside the kit folder, so it is in the release zip and in `MANIFEST.sha256`. The zip unpacks only the kit folder; the files the kit installs outside it are placed by the human using the map.
  7. **Build pieces.** (a) #113 the map and parser, (b) #114 `kit-check` and `kit-compare` read the map, (c) #115 an installed-files step in the forward import, (d) #116 the reverse import writes a feedback bundle, (e) #117 a human-only git-only comparison of the push check, (f) #118 the release procedure notes installed files. Each was filed as its own issue after approval.
  8. **The two kit copies under `vuln-triage/`** (`vuln-triage/agent-kit/` and `vuln-triage/_docs/agent-kit/`): option 3, keep both for now. Once the reverse import and feedback bundle exist (piece d), run a read-only comparison of each against the pristine kit and against each other, then the human decides which to keep. No agent deletes either one.
- **Reason:** Installed files drift unseen, and feedback from a project came from hand-made bundles that miss files and carry personal values. The map is kit data, not project settings, so it belongs in the kit folder rather than in `agent-kit.conf` (per project, editable, and it could silently narrow what is checked). It also should not change the manifest's plain hash-list format.
- **Alternatives:**
  - The map in `agent-kit.conf`: rejected, per-project and editable, mixes personal values with kit facts.
  - The map in `MANIFEST.sha256`: rejected, it is generated at release, holds only hashes of kit-folder files, and cannot hold allowed-to-differ lines; extending it changes a shared format.
  - Each reader parses the map its own way: rejected, the readers could disagree.
  - Build #7's recipe-drift check on its own first: rejected, it is the same comparison the map enables.
- **Trade-offs:**
  - One new file and one new format, and every reader must use the shared parser, with refusal tests.
  - The shared scan and check scripts run live from the working tree, so a change to them changes the guards for the change itself.
  - The push check on the human's machine cannot be checked by a sandbox tool, so a sandbox `make kit-check` can never prove it is current.
  - `markers` and `prefix:` rules let a project's copy differ in those lines without drift.
  - Because this record was rebuilt, the wording of items 1 to 8 is the reconstruction's, not the approved text's.
