# Changelog

What changed in each kit version, and what an existing project must do about it. Newest first. Reader: the human upgrading a project; the steps themselves are in `install-and-upgrade.md`.

## Changes in 1.11

Not released yet. Each entry says what was added or changed, and any behaviour change it makes.

**Settings and vocabulary**
- **Kit settings, profiles and the grade vocabulary** (`customizing.md`, `scripts/settings.py`, the `settings` target, `templates/agent-kit.conf.template`; #196): every kit value the 1.11 process uses is a setting with a kit default, changed by one `NAME=value` line in `agent-kit.conf` or set in groups by `PROFILE=solo|team|fleet`. `make settings` prints each value and where it comes from, and refuses unknown names, bad values and malformed lines with the line number. `customizing.md` lists the settings, the profiles and the Reasoning, Effort and Impact grades. Nothing reads the settings yet: each later 1.11 entry states any behaviour change its setting makes. Existing projects: no action needed. To get `make settings`, add the target from `templates/Makefile.mk`; to see the settings in your conf, copy the commented block at the end of the conf template. If your `agent-kit.conf` holds variables of your own, `make settings` refuses them by name until they move out.
- **Per-issue overrides, recorded session rulings and waivers, and bounds** (`customizing.md`, `scripts/settings.py`, `scripts/github_api.py`, the `settings` target, `process.md`, `procedures/orchestrator-comments.md`, `team/pm.md`, `templates/agent-kit.conf.template`; #197): `make settings N=<n>` resolves five levels: kit default, profile, project line, then the issue override (an `Overrides: NAME=value, ...` body line) and the session ruling (`Ruling: NAME=value` in an owner `Orchestrator: Ruling` comment with a `Human ruled:` date). The orchestrator now runs `make settings N=<n>` before each Engineer and QA launch, right after the hash check, and a refusal stops the launch. An `Overrides:` line takes effect only when the issue also has the `overrides` label, which the human creates once and adds per issue. `Waiver: <gate> - <reason>` lines in a ruling comment are parsed and checked but not yet acted on (#218). New setting `WAIVABLE_GATES` (default `heavy-second-qa,qa-recheck`; `WAIVABLE_GATES=none` refuses every `Waiver:` line), set by a project line only. No override or ruling can set `PROFILE` or `WAIVABLE_GATES` or `HEAVY_SECOND_QA=off`. `make issue-dump` now adds a `repositoryOwner` field. Existing projects without overrides: no action needed. To use `make settings N=<n>`, update the `settings` target from `templates/Makefile.mk` and copy `scripts/settings.py` and `scripts/github_api.py`; create the `overrides` label before the first `Overrides:` line.
- **Fixed fields for reports, with a recommendation required** (`procedures/formats.md`, `scripts/check-format.py`, the `check-format` target, `team/qa-engineer.md`, `team/pm.md`, `team/software-engineer.md`, `procedures/asking-the-human.md`, `process.md`, `templates/Makefile.mk`, `templates/Makefile.github.mk`; #198): every role ends with a ten-line role return (`Status:` to `Checkpoint:`, then any approval request or decision question in full). A finding is eleven lines whose labels map to the findings-log JSON keys, with ids `F-<issue>-<n>`. A QA comment keeps line 1 `QA: PASS` / `QA: FAIL`, then `Commit:` (replacing "Checked at") and `Findings: <n> fail / <n> log`, then the findings; the "Outside the criteria" list becomes findings with `Criterion: none`. A message to the human starts `Needs you:` with one block per decision or ship-or-fix, each with `Impact:` and `Recommended:`. `Recommendation:` and `Recommended:` are never empty (`none` only as `none, because <reason>`). `make check-format KIND=<return|finding|qa|message> FILE=.scratch/<name> [N=<n>]` checks the shape; nothing runs it automatically yet. `issue-file-ok` moved from `Makefile.github.mk` to `Makefile.mk`. Existing projects: add the `check-format` target and move `issue-file-ok` (with `issue-file-chars` and `issue-strip-chars`) into the GitHub-issues section of your Makefile if it isn't there; copy `scripts/check-format.py` with `scripts/settings.py`.
- **QA verdict by impact, and failing findings routed by points** (`team/qa-engineer.md`, `team/software-engineer.md`, `process.md`, `customizing.md`, `procedures/formats.md`, `procedures/asking-the-human.md`, `procedures/orchestrator-comments.md`, `scripts/check-format.py`, `scripts/route-findings.py`, the `route-findings` target in `templates/Makefile.mk`; #199): QA fails an issue exactly when a finding fails, that is, its impact is at or above `QA_FAIL_AT` and it is `Scope: in` (or `QA_SCOPE_STRICT=no`), in both QA launches; a **Verify** failure that a clean copy of the base also shows is logged, never a FAIL. `make check-format KIND=qa N=<n>` now reads `agent-kit.conf` and the dump (run `make settings N=<n>` first) and refuses a verdict or counts that don't follow from the findings, and a `Related:` id of the issue that no earlier finding holds. New category `criterion`. `make route-findings N=<n>` prints each failing finding's points (effort S=1, R=2, E=3, plus failed re-checks of its `Related:` chain), rounds, route (engineer, human or ship) and patchwork guard; the orchestrator runs it after each QA FAIL. Every ship-or-fix question has three answers (fix, ship, amend), and its block gains `Points:`. A fix check runs after each fix, at most `FIX_CHECK_LOOPS` times; a second failure in a chain opens the next fix round with an approach review; re-checks are scoped by `RECHECK`; `STEP_UP` adds a note in Claude Code. The Heavy second launch runs again only after a fix that follows its own FAIL. Changed defaults, each with the `agent-kit.conf` line nearest the old behaviour:
  - `QA_FAIL_AT=M`: a Low finding no longer fails. Old behaviour: `QA_FAIL_AT=L`.
  - `QA_SCOPE_STRICT=yes`: an out-of-scope problem no longer fails the Heavy second launch. Old behaviour: `QA_SCOPE_STRICT=no`.
  - `RECHECK=changed`: a re-check covers the failed and touched criteria, with **Verify** in full. Old behaviour: `RECHECK=full`.
  - `ASK_AT=4`: a finding goes to the human at 4 points. Old behaviour (no limit): `ASK_AT=99`.
  - `FIX_CHECK_LOOPS=2`: new; no value turns the fix check off.
  - `STEP_UP=ask`: a step-up note in the next message to the human (Claude Code only). Old behaviour: `STEP_UP=off`.

  Existing projects: add the `route-findings` target from `templates/Makefile.mk`, copy `scripts/route-findings.py` with `scripts/check-format.py` and `scripts/settings.py`, and run `make settings N=<n>` before each `make check-format KIND=qa`. Add the lines above to `agent-kit.conf` to keep the old behaviour.
- **Findings log, `make findings` and the sweep's findings step** (`procedures/formats.md`, `procedures/sweep.md`, `procedures/asking-the-human.md`, `procedures/orchestrator-comments.md`, `process.md`, `team/qa-engineer.md`, `team/software-engineer.md`, `team/pm.md`, `customizing.md`, `scripts/findings.py`, the `findings` target in `templates/Makefile.mk`; #200): an unfixed finding at or above `FINDINGS_TO_ISSUE_AT` gets an unlabelled draft issue; a lower one becomes an entry, with a group, in `_docs/records/findings/<issue>.json`, which the orchestrator writes once at close (a shipped finding gets its follow-up issue and is not logged). The sweep's outcome per entry (`issued`, `dropped`, `kept`, `regroup`) goes in the append-only `_docs/records/findings-rulings.jsonl`. `make findings` lists the open entries by group with age in sweeps and debt counts, and refuses a bad file or line by name. The sweep runs it, drafts one issue per group at `FINDINGS_GROUP_AT`, brings entries open for `FINDINGS_KEEP_SWEEPS` sweeps to the human to keep or drop, and counts amended criteria per issue. The Engineer marks a deliberate shortcut with a `shortcut:` comment and a `Category: debt` finding; QA reports any `shortcut:` comment without one, and reuses a group slug that `make findings` lists. The logged findings of #196 to #199 are migrated to the format. New defaults:
  - `FINDINGS_TO_ISSUE_AT=C`: only a Critical unfixed finding gets its own issue; the rest is logged. Old behaviour: `FINDINGS_TO_ISSUE_AT=L`.
  - `FINDINGS_GROUP_AT=5`: five open entries in one group get one draft issue at the sweep. Old behaviour: `FINDINGS_GROUP_AT=99`.
  - `FINDINGS_KEEP_SWEEPS=5`: an entry open for five sweeps goes to the human to keep or drop. Old behaviour: `FINDINGS_KEEP_SWEEPS=99`.

  Existing projects: add the `findings` target from `templates/Makefile.mk`, copy `scripts/findings.py` with `scripts/check-format.py`, `scripts/settings.py`, `scripts/sweep-due.py` and `scripts/github_api.py`, and add the lines above to `agent-kit.conf` to keep the old behaviour. Entries are logged from the first issue closed after the upgrade; write earlier ones by hand in the format of `procedures/formats.md` if you want them counted.
- **The numbered criteria as the Engineer's and QA's shared checklist** (`team/pm.md`, `team/software-engineer.md`, `team/qa-engineer.md`, `procedures/planning.md`, `procedures/formats.md`; #201): a criterion's `Check:` line must be something QA can run or read without asking the PM, and Plan review has an item for it. The Engineer's issue comment holds a `Criteria list` with one line per criterion, in order: `C<n>: done (<evidence>)`, `C<n>: not done`, `C<n>: not checked (<reason>)` or `C<n>: challenged (<reason>)`, defined once in `procedures/formats.md`. QA reads that list first, still checks every criterion itself, and names any disagreement on its own `Criteria` line (an unresolved `challenged` goes to the human). No script reads the list and `check-format` has no new kind. No setting or default changes. Existing projects: copy `team/pm.md`, `team/software-engineer.md`, `team/qa-engineer.md` and `procedures/formats.md`, and `procedures/planning.md` for the plan-review item. - **A standards register and a `Standards:` line on issues** (`templates/task-template.md`, `templates/standard.md`, `templates/docs-index.md`, `team/pm.md`, `team/software-engineer.md`, `team/qa-engineer.md`, `procedures/formats.md`, `blueprints.md`; #202): a standard is a short file (at most 120 words: rule, why, when it applies, check, added by) in `_docs/standards/`, from `templates/standard.md`; the docs index template gains a `Standard` row, added when the first standard exists. QA runs each listed standard's check (a `make` target the project provides, or reading the file) in every launch and re-check: a breach is `Category: standard`, `Scope: in`; a breach of an unlisted standard is `Scope: out`, logged, never failing under `QA_SCOPE_STRICT=yes`. The kit adds no runner. No setting or default changes. Existing projects: copy `templates/task-template.md`, `templates/standard.md`, the role files (`team/pm.md`, `team/software-engineer.md`, `team/qa-engineer.md`), `procedures/formats.md` and `blueprints.md`, and add the `Standard` row of `templates/docs-index.md` to your `_docs/index.md` with your first standard; write `Standards: none` on issues groomed before this. - **Grooming ahead, a place in the order for every issue, and a re-check before the Claim** (`process.md`, `team/pm.md`, `procedures/orchestrator-comments.md`, `templates/roadmap.md`, `customizing.md`; #203): the PM may groom up to `GROOM_AHEAD` issues ahead of the one in progress, in the agreed order. An issue counts as groomed ahead when a valid `PM:` hash record matches its body and it hasn't started. Grooming beyond the limit, or an issue with no place in the order, is refused by the orchestrator's reading and counting; no script does it. The agreed order is the ordered list of the roadmap file the docs index names, each entry with its trigger, and every filed issue is added in the session it is filed. The orchestrator sets a `[groomed]` title prefix once the hash matches and removes it when the body changes; counting uses the hash, never the title. The two paths of approval are written down: groom first (`Grooming authorised by: human in session, ...` then `Approved by: approved label, seen <date>` in the Claim) and label first (`approved` means "you may groom", then `Approved by: human confirmation in session, <date>` in a Confirm comment). The PM records `Groomed at: <sha>`, and before the Claim the orchestrator reads `git diff --stat <sha>..HEAD` for the issue's Files paths and has the PM re-check on an overlap. Changed default: `GROOM_AHEAD=2` (the `solo` profile) grooms two ahead. Old behaviour, one issue at a time: `GROOM_AHEAD=0`. Existing projects: copy `process.md`, `team/pm.md`, `procedures/orchestrator-comments.md`, `templates/roadmap.md` and `customizing.md`; add `GROOM_AHEAD=0` to `agent-kit.conf` to keep today's rule; otherwise put your open issues in order in a roadmap file with a trigger each, and add each new issue to it as it is filed. - **Decision points graded by Impact and Effort, a ledger of the ones continued past, and per-point answers** (`process.md`, `procedures/asking-the-human.md`, `procedures/formats.md`, `procedures/orchestrator-comments.md`, `team/software-engineer.md`, `customizing.md`, `scripts/decisions.py`, `scripts/check-format.py`, the `decisions` target in `templates/Makefile.mk`; #204): a decision point is a choice made while the work runs that the issue doesn't settle, and the questions met at one stop are one point; mechanical steps never ask. It carries `Impact:` and `Effort:` (the rework if the answer changes), whose points are S=1, R=2, E=3 as for findings. Thirteen stop kinds always wait for the human (`spec`, `security`, `money`, `irreversible`, `outside`, `dependency`, `protected`, `scope`, `reasoning`, `approach`, `ship`, `amend`, `gate`), as does a return with `Needs the human: yes`. The one continue kind, `choice`, is taken on its recommendation and logged with its rollback and dependents while the open continued points, counted over every issue, stay within `DECISION_BUDGET`. The ledger is `_docs/records/decisions/<issue>.jsonl`, append-only, with the events `open`, `answer` and `reworked`. `make decisions [N=<n>]` refuses a stop kind logged as `continue` and any malformed line, and lists open points, rework items and `within budget`, `budget reached` or `over budget`; the orchestrator runs it after `make settings N=<n>` before each Engineer and QA launch, puts every open point in the decision-point message, and doesn't close an issue with an open point or unfinished rework. The human answers per point (`D-12-1 approve`, `D-12-2 q2=B`, `D-12-3 reject`); `reject` or another option on a continued point makes a rework item. The decision block of the message gains `Effort:` and, for a continued point only, `Rollback:`, which `make check-format KIND=message` checks; `Point:` and `Weight:` lines are refused. A commit that depends on an open point isn't pushed (direct to `main`) or merged (branches) until the point is closed; a cloud session's own `claude/*` branch may carry such commits, but its pull request waits. The Close comment lists each decision point. Changed default: `DECISION_BUDGET=3` now acts. Before, every choice waited, uncounted, for the end of the issue; `DECISION_BUDGET=99` comes closest to that, and `DECISION_BUDGET=0` is stricter than before (every point stops). Existing projects: add the `decisions` target from `templates/Makefile.mk`, copy `scripts/decisions.py` with `scripts/check-format.py`, `scripts/settings.py` and `scripts/github_api.py`, and copy the docs above; add `DECISION_BUDGET=99` to `agent-kit.conf` to stay closest to the old behaviour. Expected word change (`wc -w`, before to after): `process.md` 5036 to 5910 (+874), `procedures/asking-the-human.md` 1481 to 1719 (+238), `procedures/formats.md` 1299 to 1678 (+379), `procedures/orchestrator-comments.md` 450 to 449 (-1), `team/software-engineer.md` 950 to 1095 (+145), `customizing.md` 3495 to 3584 (+89), `README.md` 2502 to 2508 (+6), `CHANGELOG.md` 5222 to 5638 (+416).
- **Reflections written to files at the end of every launch** (`templates/reflection.md`, `procedures/formats.md`, `process.md`, `procedures/session-summary.md`, `templates/session-summary.md`, `procedures/sweep.md`, `blueprints.md`; #206): there is no reflection launch after QA PASS any more. The ten-line role return and `make check-format KIND=return` are unchanged. - **Numbered acceptance criteria** (`templates/task-template.md`, `team/pm.md`; #196): each criterion is written `- [ ] C<n>. <statement>` with an indented `Check:` line saying how it is verified, and keeps its id once the issue is approved. Existing projects: nothing; groom new issues with the new template.
- **Git guard hardening** (`claude-code/hooks/guard_git.py`, `claude-code/settings.json`): the PreToolUse guard now reads unambiguous long-option prefixes (`--no-ver`, `--al`), checks `git add` short clusters (`-Av`, `-uA`), blocks `git -c core.hooksPath=...` and `--config-env=core.hooksPath=...` in any case, and no longer mistakes a commit message for a flag (`git commit -m "--no-verify"` is allowed). When a command cannot be parsed, a raw scan still blocks `git push`, `--no-ver`, `core.hooksPath`, broad `git add` and `.env`. It fails closed: invalid input, an unexpected payload or an internal error exits 2, and the settings register the hook as `python3 ... || exit 2`, so a crash blocks. - **CodeBuddy layer** (`codebuddy/`, `.codebuddy/`): CodeBuddy reads `AGENTS.md` when no `CODEBUDDY.md` exists, so `AGENTS.md` stays the single always-loaded core-rules home and the kit adds no `CODEBUDDY.md`. It runs the Claude Code git guard in place, with `|| exit 2`: CodeBuddy treats any non-zero exit other than 2 as a non-blocking error, so the wrapper is what turns a guard crash into a block. `STEP_UP` stays Claude-only, as in OpenCode and Kiro, and the kit configures no model swapping. - **Antigravity CLI layer** (`antigravity/`, `.agents/`): Antigravity reads `AGENTS.md` directly and walks parent folders up to the checkout root, so `AGENTS.md` stays the single always-loaded core-rules home and the kit adds no pointer file or copy. The layer is `antigravity/START.md`, `antigravity/hooks.json` (merged into `.agents/hooks.json`), the three agents in `antigravity/agents/` (`.agents/agents/`) using Antigravity tool names (`view_file`, `grep_search`, `write_file`, `run_command` and `replace_file_content` for Engineer only), and `antigravity/guard_adapter.py`. The PreToolUse hook adapter translates Antigravity's `run_command` payload into the shared git guard's input and emits an explicit decision on every path, never exiting 0 silently (a hook exiting 0 with no output fails open; malformed JSON, exit 1, and timeouts fail closed). No permissions file ships in the repository: Antigravity reads permissions only from the global file `~/.gemini/antigravity-cli/settings.json`, documented as a human step. Existing projects: no action unless you use Antigravity CLI; then follow `antigravity/START.md` and add `'.agents/*'` to `PROTECTED`.

## Changes in 1.10

1.10 is the first release that ships a `MANIFEST.sha256` (see `releasing.md`), so a project can import it by `procedures/kit-import.md` and compare with `make kit-check`. Each change says what an existing project must do. A project last at 1.9 should do them all, in the order of the situation that fits in `install-and-upgrade.md` (situations 4 to 6).

**Not verified in a real run** (shipped as written; none changes what an existing project must do): the Compose variant, the push-check image, the OpenCode permission rules on 2.2.5 (the 2026-11-04 re-run was not comparable), `pipx` run directly in the dev container, and the CI template's action major versions (the first CI run confirms those). Verified in a real run: the dev container pins and clean-clone refusal (rebuild check, 2026-11-07) and the OpenCode 2.2.5 permission-log plugin (2026-11-08). Known gaps: this repo's own `.devcontainer/` still lags the reference, and merge commits still skip the `HUMAN_APPROVED` gate.

**Process and roles**
- **Tiers and Heavy gates** (`process.md`, `team/`, `scripts/check-tier.sh`, `make tier-check`): Light, Standard and Heavy tiers with a path limit per tier; Heavy needs an ADR before the Engineer starts and a second fresh QA launch. QA gets a code-review checklist. Existing projects: add the `tier-check` target; nothing else unless you want tiers.
- **Grooming and approval** (`process.md`, `team/pm.md`): the PM grooms before approval, the approved body is frozen by hash (`make issue-hash`), and `approved` can also approve the PM's Standard or Heavy tier proposal. Existing projects: add `issue-hash`; the label rules already in your `AGENTS.md` still hold.
- **Planning** (`procedures/planning.md`, the spec definition of ready, spec notes layout, roadmap template, optional Design section in the issue template): one intent per issue, a testable example, a plan-review checklist. Existing projects: nothing; use the new templates when you next file an issue or plan.
- **Templates and records** (`templates/`): the issue template's required Why section, a GitHub issue intake form, the pull request template (`Refs #N`, never `Closes`), human task files, the docs index with entry-type folders and starter docs, decision records linked to their evidence. `make dup-report` lists repeated sentences and decision keys with differing status (read-only, never a gate). Existing projects: copy `templates/github/ISSUE_TEMPLATE/` and `templates/github/pull_request_template.md` into your `.github/` if you want them; add the `dup-report` target.
- **Procedures**: the orchestrator comments procedure (claim, release, confirm and close comments start with `Orchestrator:`), a periodic sweep procedure with skill wrappers, the Report by reference rule, and the session-summary reflection and launch usage lines. Existing projects: copy the kit folder; copy the sweep skills (`.claude/skills/sweep/`, `.opencode/skills/sweep/`) if you use them.

**`AGENTS.md`**
- The template changed since 1.9, most recently on 2026-11-21 so that Enforced by hooks names CodeBuddy's hook as well as Claude Code's; otherwise the shared block is as it was since 2026-11-03 (`67153ed`; the permission, install and release changes after that did not touch it). The shared block is Non-negotiables, Enforced by hooks and Read when, bracketed by `SHARED START` and `SHARED END`; the project half gains a `Readable config` line (default `none`), a `Fetch an issue` command and a session-summaries line. Existing projects: update the shared block with Prompt C in `install-and-upgrade.md`; keep the project half and add the new lines.

**Scripts, Makefile and hooks**
- **Issue wrappers** (`scripts/issue-create.sh`, `issue-comment.sh`, `issue-close.sh`, `issue-hash.py`, `secret-patterns.txt`; `make issue-dump`, `issue-hash`, `sweep-due`): create and comment through a secret scanner and an owner check; `issue-close` can close an issue and nothing else. Existing projects: copy `scripts/` and the new `Makefile.mk` targets.
- **Safer file handling** (`scripts/check-staged.sh`, `verify.sh`, `check-tier.sh`, `assert-clean.sh`, `githooks/pre-commit` version 4, `githooks/pre-push`, `claude-code/hooks/verify_on_stop.py`): changed names are read NUL-delimited, so non-ASCII and quoted names are checked, and the checks fail closed. A make variable is validated without being expanded. Existing projects: copy `scripts/`, then run `make hooks`, which upgrades the hooks.
- **Claude Code git guard** (`claude-code/hooks/guard_git.py`, `claude-code/settings.json`): also blocks shell commands naming `.env` files (not `.env.example`) and has a stricter allow-list and ask rules. The OpenCode permission template has safer read-only allows and more command patterns (`opencode/opencode.json`). The settings-read rule is narrowed: a project may list committed config files under `Readable config`. Existing projects: the hooks run in place from the kit folder; merge the settings by review, because `.claude/settings.json` and `opencode.json` are merged, not copied.
- **Project bootstrap** (`scripts/bootstrap-project.sh`): the human runs it once from a plain folder to create the clean clone and sandbox folder, install the push check and copy the tracked kit files, the recipe and the CI template; it refuses a kit with unpushed commits or uncommitted changes. Existing projects: nothing.
- **Claims check** (`scripts/check-claims.py`, run by `make test` in this repo): fails when a doc names a make target or file the kit doesn't ship. Existing projects: nothing.

**Permission logs** (optional)
- **OpenCode plugin** (`opencode/plugins/permission-log.js`, the OpenCode 2 plugin API) and a **Claude Code logger** (`claude-code/hooks/log_permission.py`) record each permission prompt; `make permission-report [SINCE=<YYYY-MM-DD or YYYY-MM-DDTHH:MMZ>]` summarises both and `make permission-logs-prune DAYS=<n>` deletes old logs (the human runs it). The logger refuses a symlinked log folder or file and the plugin resubscribes when the event stream ends. Existing projects: to use OpenCode's log, copy `.opencode/plugins/permission-log.js` from a clean clone (it needs OpenCode 2.2.5 and replaces any 1.x plugin); for Claude Code, merge the hook entry from `claude-code/settings.json`. Skip both if you don't want logs.

## Changes in 1.8

- **Claude Code layer** (`claude-code/`, start at `START.md`). It replaces the separate Claude Code-only kit 1.0 used in Table Ready, and brings it fully up to date with the core kit:
  - role definitions that point to `team/`: the PM edits files only under `.scratch/` by instruction, QA can't edit files, and the Engineer carries a hook that re-runs `make verify` before it can finish;
  - a git guard hook that blocks broad staging, `commit -a`, `--no-verify`, `git push` and `core.hooksPath` changes before they run;
  - settings with the allow-list, ask rules for protected files, deny rules for `.env` files and `git push`, and commit attribution. The git guard also blocks shell commands naming `.env` files (not `.env.example`); indirection such as `bash -c "cat .env"` is a known gap for both tools. The OpenCode template denies shell commands naming `.env` files by a text pattern, not a boundary.

  The hooks run in place from the kit, so kit upgrades update them.
- **Existing agent setups:** setup no longer needs to know where a project's current setup came from. It reads each existing agent file, works out what it does, and classifies it against the kit: superseded, merged, kept or flagged as a conflict. That covers older kit versions, other kits and hand-built tool configurations alike.
- **Setup** asks which AI tools you use, and installs the Claude Code layer when it applies.

## Changes in 1.7

- **Asking the human:** a new procedure, `procedures/asking-the-human.md`. Every command's description says what it does and why, naming the issue and step. Anything that needs approval on its merits gets an approval request before the command runs: what and why, the exact command, risk and undo, alternatives, and a recommendation. Decisions come as decision questions with options and a recommendation.
- **Subagents:** the human can't see a subagent's messages, so a subagent returns its request to the orchestrator instead of running the command. The orchestrator passes the request on in full and resumes the role with the answer.
- **Approval requests also cover:** whether the request came up before; a check run just now for any addresses or IDs in the command; risk with duration; and alternatives that fix the cause or let the human run the command, so agents don't need `sudo`.
- **Known environment issues:** a new blueprint. A problem that needed the human's fix more than once gets a README entry (symptom, check, fix, undo), which later requests point to.
- **Deletions and safety blocks:** agents don't delete files or data they didn't create, including git-ignored files and Docker volumes, which **Assert clean** can't see. When the tool blocks an action as risky, the agent stops and reports instead of trying variations. The orchestrator then shows the human each blocked command, checks what changed, and proposes resuming or starting the role fresh.
- **Destructive checks:** when checking a criterion needs a destructive step, such as deleting a Docker volume, the PM says so when grooming, and the human performs that step.
- **`make clean-scratch`:** a new core target. At the end of every issue the orchestrator empties `.scratch/`, including test tokens and copied session logs, after proposing any script worth keeping as a test or make target. It refuses while a process started with `<name>-start` is still running.
- **Upgrades:** the upgrade prompt asks for the exact `git add` paths, including the kit folder.
- **Commit attribution:** a new blueprint. AI-assisted commits carry one plain line, "Generated with Claude Code", set in the tool's settings, with no co-author email or model version. Agents don't add their own co-author lines.

## Changes in 1.6

- **Conventions:** one list of shell forms to avoid, with replacements; files are edited only with the tool's editor; no reading the tool's settings, the home folder or environment variables; servers start and stop through make targets or `.scratch/` scripts, and agents stop only processes they started; bypass attempts go in tests or scripts; requests for system changes include the undo command; large `.scratch/` installs need asking and are deleted afterwards.
- **Process:** a standard launch message for roles; one decision point after QA passes; clean-up before the session summary; a procedure for a role that stops early.
- **PM:** decides edge cases itself and asks only about scope, interfaces, the spec or security limits; every limit says how it's enforced, with a case that must be refused; fixed text records where it comes from; spec notes are collected, not stopped for.
- **Engineer:** lists choices the issue doesn't cover and spec notes; adds a stub setting for anything that starts a paid or external process.
- **QA:** a fuller comment layout; tries to get around every limit; reports risks outside the criteria separately from the verdict.
- **Blueprints:** start/stop targets, the stub setting and role definitions for tools with named subagents. The session summary template gains decisions, temporary changes and interruptions.
