# Decision: The deploy role also trusts the `deploy-prod` Environment, and the instance role also reads the prod secret

One file per choice that may be revisited. **Status: proposed** (Heavy tier: it changes who may assume a CI role and what the instance may read, a security boundary in code; only the human sets `approved`). Issue #268 (body hash `20d8c1f7c6668a2d6ff104da17b0a714b226c732fa7fa2a5a8991a86fe0489a2`). It applies item 3 of the approved dev and prod record (`2026-11-15T1840Z-dev-prod-one-server.md`) and adds no new rule beyond these choices. The AWS and GitHub details are unchecked until the maintainer's apply (`VERIFY:` comments in `terraform/ci-access/deploy.tf` and `terraform/iam-and-budgets/main.tf`).

- **Decision:** the existing role `socboard-ci-deploy` trusts two exact subjects, `<prefix>:environment:deploy` and `<prefix>:environment:deploy-prod`, where `<prefix>` is the numeric-id form `repo:<owner>@<owner id>/<repo>@<repo id>`, both with the audience `sts.amazonaws.com`, as a list under one `StringEquals` condition. The role's permissions do not change. The instance role's one inline statement allows `secretsmanager:GetSecretValue` on exactly two ARNs, `socboard/app` and `socboard/app-prod`, each set by a variable that validates the exact name. The apply and plan roles, the outputs and every other statement stay as they are. Both parts stay human-applied. The role's unique ID (`AROA...`), which the credentials action prints, is masked through one repository secret, `AWS_DEPLOY_ROLE_ID`, because both Environments use the same role.
- **Reason:** the approved record chose one server and one role; the role already holds the one right prod needs (sending the one deploy document). A list of exact strings is the narrowest way to add a subject: with no pattern, no other Environment name can match. Naming exact ARNs keeps the instance's secret access to the two secrets the stacks use.
- **Alternatives:** a second role `socboard-ci-deploy-prod` (AWS could then be given a prod-only right, but it needs a new role, a new ARN secret, a second ID to mask and a larger change than "nothing wider"; a follow-up if wanted); `StringLike` with `deploy*` (matches any future Environment, rejected); a secret ARN pattern `socboard/app*` (reads any secret with that prefix, rejected); a list variable for the secrets (renames `app_secret_arn` and breaks the maintainer's existing variable file for no gain).
- **Trade-offs:**
  1. The role cannot tell a dev job from a prod job, and its rights are the same for both. The deploy script's environment parameter (#267) picks the stack, not AWS, so a job in `deploy` (no reviewer) on `main` could be written to deploy to prod. The controls are GitHub's: the `deploy-prod` reviewer gate applies only to a job that names that Environment, and a workflow change reaches `main` by a reviewed pull request. A separate prod role is the way to make AWS enforce it.
  2. As with `deploy`, the branch limit is the Environment's own setting, not AWS. If `deploy-prod` lacks its `main` rule, any branch that names it can assume the role. The refused-branch run (and its positive control) is the evidence.
  3. The instance reads both secrets, so a compromise of the host reaches both (already accepted in the approved record).
  4. Every change here is a manual apply by the maintainer.
  5. A `terraform test` cannot show that no `data` source reads a secret, because a test reads only what it names; the review of the diff covers that, and the folders hold none.
