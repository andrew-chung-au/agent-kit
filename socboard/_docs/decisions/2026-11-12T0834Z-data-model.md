# Decision: SQLAlchemy 2.x models and Alembic migrations, with one conditional UPDATE for single ownership

Heavy tier: the schema is an interface every later issue depends on, it carries the one-owner and append-only rules, and it adds dependencies and touches protected files.

- **Decision:** Use SQLAlchemy 2.x models with Alembic migrations, SQLite for Core. Table names are plural. Primary keys are database-assigned integers, exposed as decimal strings through one helper pair (`to_public_id`, `from_public_id`), as decided by the human. Enumerated values are constrained strings (named CHECK constraints) built from one list that a test compares with `openapi.yaml`. The closing reason is guarded by two database CHECK constraints (reason present if and only if the status is Closed), as decided by the human; the choosing logic and the 422 `reason_required` stay with #17. The database URL is read from `SOCBOARD_DATABASE_URL`, as decided by the human. Timestamps use one UTC-only column type. One function, `append_audit`, writes audit entries inside the caller's transaction. The audit trail is append-only in the database: triggers on `audit_entries` refuse any UPDATE, any DELETE and any INSERT that reuses an id, and a named CHECK `id >= 1` on `audit_entries` (`ck_audit_entries_id_positive`) keeps the id-reuse trigger usable: SQLite gives `NEW.id` the value -1 when no id is supplied (tested on SQLite 3.46.1 and 3.40.0), so the trigger tests only whether a row with `id = NEW.id` exists, and without the CHECK one row with id -1 would make every later plain insert, and so every `append_audit`, fail; the id rule for the other tables is unchanged; an application-layer guard refuses DDL on the table and repeats the UPDATE and DELETE checks as a second layer. The human ruled this (option B) on 2026-11-12. **Single ownership** is enforced by one conditional UPDATE and one nullable column. The owner is `cases.owner_id`, one nullable foreign key; the human decided to drop the assignment table, so there is none, and assignment history is the `claimed` and `reassigned` audit entries. A claim is the statement `UPDATE cases SET owner_id = :user_id WHERE id = :case_id AND owner_id IS NULL AND status <> 'Closed'`, executed once in the claimant's transaction. One row changed means the claim won; no row changed means it lost, and only then does the code read the case to choose between 404 `not_found`, 409 `case_closed` and 409 `already_claimed`. The code never reads the owner first and then writes. The `claimed` audit entry is appended in the same transaction only after the row count is 1. #16 implements this and tests concurrent claims.
- **Reason:** The spec says exactly one of two simultaneous claims wins on any supported database. A single conditional UPDATE is atomic on SQLite and on Postgres and cannot leave two owners because there is only one owner column. It needs no application lock. On Postgres it needs no retry at READ COMMITTED (the second statement waits, re-checks `owner_id IS NULL` and changes no row); at REPEATABLE READ or SERIALIZABLE the loser gets a serialization failure, so the application runs at READ COMMITTED. On SQLite the loser waits for the write lock and gets `database is locked` if the winner's transaction outlasts the busy timeout, or at once if its own transaction read before the claim under a real `BEGIN`; #11 keeps the driver's default transaction mode and a 5 s busy timeout (both tested clean), never `BEGIN IMMEDIATE`, and #16 decides what a lock timeout answers. A read-then-write check, or a second table holding assignments, allows a window or a disagreement between two records of the owner. Alembic is the standard migration tool for SQLAlchemy and gives a reviewable history. Constrained strings behave the same on SQLite and Postgres. Integer keys give a stable "as stored" order for audit entries and notes. One audit function is simple to test. Append-only is enforced in the database because an application guard that lists constructs missed ordinary SQLAlchemy forms in three independent reviews (aliases and case variants, then `lambda_stmt` and `table()`); only the database sees every write, whatever form it was built in, and the spec makes the audit trail append-only.
- **Alternatives:** A read-then-write claim inside a transaction (needs `SELECT ... FOR UPDATE`, which SQLite lacks); a version column with retry (more code for the same result); an assignment table as the owner of record (two sources of truth); opaque string keys such as UUIDs (no insertion order for audit entries without a second column); hand-written SQL migrations (no new dependency, easy to get wrong); database enum types (Postgres-only features); an application-layer guard only (the earlier choice; ordinary constructs such as aliases, case-variant names, `lambda_stmt` and `table()` got past it); record the gaps as accepted (honest but weak for a SOC audit trail).
- **Trade-offs:** What can still bypass it: raw-SQL DDL and DML sent through `text()`, `exec_driver_sql` or a DBAPI cursor, and direct access to the database file. That includes `DROP TRIGGER`, a raw `UPDATE sqlite_sequence`, and `PRAGMA ignore_check_constraints` and `PRAGMA writable_schema` sent as raw SQL; the application guard refuses the same things only when they are built with SQLAlchemy constructs (and, for DDL outside `socboard/migrate.py`, as `DDL(...)`). All of these are deliberate acts, not accidental routes. How each rule of the guard works is in `socboard/audit_guard.py` (its module docstring and `supplies_audit_id`); this record keeps only what is still open. **The id rule (#99, changed by #107):** the guard refuses an INSERT into `audit_entries` whose `id` can come from the caller (the id is database-assigned and `append_audit` never supplies one), and it no longer compiles the statement to find out. It refuses anything in the `id` position of `values()` (any row) other than None or NULL, so a `bindparam` there is refused whatever its execute value; the `id` of `from_select`; and an execute-parameter key `id` or `id_m<n>` (the name SQLAlchemy gives the `id` of row n of a multi-row `values()`) with a value other than None. The cost: a `bindparam` for `id` executed with None is refused (nothing in the repository does this), and `id_m<n>` is SQLAlchemy's naming convention: a test shows the route reaches the table without the guard and fails if the name changes, and then the pattern is updated. **Still open:** a custom `ExecutableDDLElement` subclass with an `@compiles` function that emits `DROP TRIGGER` (the guard sees no table, element or text); `CreateIndex` of a new index on a lightweight `table("audit_entries", ...)` column (it only adds an index); a custom type on `id` (a `TypeDecorator` or `bind_expression`) is not modelled, because the guard reads the Python value, not what the type turns it into; and the guard is not a SQL parser: it matches the text of a `DDL(...)` as words (a `DDL(...)` that SQLAlchemy cannot render is matched on its template alone, since it fails before it reaches the database), so a comment or string literal that names the table, a trigger, `sqlite_sequence` or one of the two pragmas makes the `DDL(...)` be refused. A future migration written as `DDL(...)` must not mention these words; the pragma and `sqlite_sequence` words are never lifted by `allow_schema_changes()`. An upper bound on the `id` CHECK was not used: a row allowed at the bound makes the next automatic id exceed it, so `append_audit` fails at the bound instead of at 2^63-1, and a bound needs a migration that rebuilds `audit_entries`. **De-duplication:** `INSERT OR IGNORE` and `ON CONFLICT DO NOTHING` on an existing audit id raise (the trigger `audit_entries_no_reuse_id`, or the guard when the id is explicit) instead of skipping, so #14 and later issues must not de-duplicate audit entries that way. A migration that inserts audit rows with explicit ids through SQLAlchemy constructs is refused, because `allow_schema_changes()` lifts only the DDL check; it must use raw SQL or change the guard with a new record. Postgres needs equivalent triggers, added in the Deploy phase with the Postgres migration. Alembic and SQLAlchemy are new dependencies and need the human's approval. Enforcing "reason only when Closed" in the database makes #17 set status and reason in one statement; that is what it must do anyway. Alembic's autogenerate does not see CHECK constraints or triggers, so the tests insert bad values into the migrated database and compare the trigger text in `sqlite_master`. A later migration that rebuilds `audit_entries` (Alembic batch mode on SQLite) silently drops the three triggers and `AUTOINCREMENT`. Such a migration must re-create the triggers from literals in its own file and pass `table_kwargs={"sqlite_autoincrement": True}`; the tests that expect the three triggers and `AUTOINCREMENT` after `upgrade head` fail if it does not. The trigger SQL is SQLite's and is written again for Postgres.
  - (added, #193) On Postgres the rule is migration `0002`'s four `ENABLE ALWAYS` triggers (update, delete, reused id, truncate); the table owner and any superuser can still disable or drop them, as the Deploy record's decision 8 (`_docs/decisions/2026-11-13T2156Z-deploy.md`) says.
  - (added, #195) Open limits of the guard on Postgres, each with the layer that covers it (`tests/test_data_audit_guard_postgres.py`): raw SQL sent through `text()`, `exec_driver_sql` or a DBAPI cursor, including `COPY` and the driver's `cursor.copy`, is outside the guard on Postgres too; COPY fires the INSERT trigger, so a reused id is still refused. The table owner and any superuser can disable, drop or replace the triggers and their trigger functions (decision 8); `DISABLE TRIGGER ALL` needs a superuser because it also touches the foreign-key system triggers, so the owner uses `DISABLE TRIGGER USER`. A role with `INSERT` can plant a future id by raw SQL or COPY (an explicit id does not move the sequence), so a later `append_audit` that draws it is refused once as "overwritten". `setval` and `ALTER SEQUENCE` on `audit_entries_id_seq` are not seen by the guard; the database refuses both to a role that holds only `USAGE` on the sequence (checked on Postgres 16).
  - (added, #214) The guard sees through `lambda_stmt`: `refused_statement` replaces a lambda by the statement it builds (SQLAlchemy's private `_resolved`) and applies every rule to it, and refuses a lambda it cannot read; before this, a lambda INSERT with an explicit id, and a lambda write to `sqlite_sequence`, got past the guard. A `lambda_stmt` that captures a `None` id from a variable is refused like a `bindparam` for `id`. Record: `_docs/decisions/2026-11-15T0846Z-audit-guard-lambda-stmt.md`.
