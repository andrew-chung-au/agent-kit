# Decision: The on-call agent runs in its own read-only job and hands back a patch that a second job checks before it pushes

One file per choice that may be revisited. **Status: approved** (the human approved this decision record by name for issue #298, whose body hash is `5ac039b2fdff3ddcf654f22ddbab1291a29da9ca2c6706b2adfdd991f04b5ebc`; the claim is https://github.com/andrew-chung-au/socboard/issues/298#issuecomment-6936715594). The text below is the issue's `## Decision record` section.

- **Decision:** the agent runs in its own job with a read-only token and the model key, and hands back a patch. A second job with no model key takes the guard from `main`, checks the patch, and only then pushes `oncall/<run id>` and opens a draft pull request. The agent's tools are an allow list with no network tools besides the model. A repository ruleset on `main` is required, and auto-merge stays off.
- **Reason:** a prompt can be ignored or overridden by untrusted incident text; a job boundary, a token permission and a check the agent cannot edit cannot. Two jobs do not share a filesystem, so the agent cannot plant a hook or change the guard the pushing job runs. The ruleset closes the gap that `contents: write` can push to an unprotected `main`.
- **Alternatives:** one job with the guard as a later step (simpler, but the agent can tamper with what the step runs); limits by prompt only (not enforced); a GitHub App with narrower scopes (a new credential); live queries by the agent against the stack (needs network tools and keeps the agent in the stack's job).
- **Trade-offs:** the agent investigates from a pre-collected bundle (the incident and fixed query results, #299), not live queries, so it cannot ask a new question of the stores. With `GITHUB_TOKEN` the pull request gets no automatic CI (#287), so #299's third job and the run log are the test evidence. The size limits may refuse a legitimate larger fix, which then needs a human.
