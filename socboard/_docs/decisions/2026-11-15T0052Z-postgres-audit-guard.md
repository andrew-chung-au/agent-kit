# Decision: On Postgres the audit guard stays an extra layer with no new rules; the database refuses what the guard cannot see

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-15, in the Postgres lane session: "approved decisions", in answer to the list of the Postgres lane's three proposed records) (issue #195, Deploy item D6b; copied from the issue's `## Decision record` section, which the human approved with the issue, body hash `d7c730abc34b9b80f470460cdbb58511d2a37ef6e1cfb27cdc5881aaa93733d4`; the PM comment's two open questions defaulted to option 1; the human's ruling at claim, recorded in the Claim comment, reads the offline criterion without a dialect argument; notes the Engineer added are marked "(added: ...)"). Only the human sets `approved`.

- **Decision:** (1) The guard stays an extra layer on Postgres and is not made an enforcement layer: no new refusal rule is added for a Postgres statement that only the owner or a superuser can run; each is recorded as a limit. (2) SQLite-only parts that never match on Postgres stay. (3) The review runs on the guard as #107 left it, because #107 merged before the claim.
  - (added: #107 landed first) #107 removed the compile step and the `dialect` parameter of `refused_statement`, so the `Session` hook has no dialect to pass and needs no change: a Postgres-only expression in an INSERT is no longer refused (a test shows it). #107 also removed the `ATTACH`/`DETACH` rule and comment stripping, so neither is reviewed here.
  - (added: found by the tests) `ALTER TABLE audit_entries DISABLE TRIGGER ALL` is refused even to the table owner, because it also disables the foreign-key system triggers, which needs a superuser; the owner can still run `DISABLE TRIGGER USER` or drop a trigger by name (decision 8).
- **Reason:** (1) The database refuses these for the application role (D6a, #193); the guard sees only SQLAlchemy constructs and `DDL(...)`, and nothing in the repository sends these statements; #107's out-of-scope line says no new refusal rule. (2) Removing parts that cannot match adds a change to a Heavy file for no Postgres benefit.
- **Alternatives:** Add Postgres words to the guard (`session_replication_role`, the trigger function names, `audit_entries_id_seq`), never lifted like the pragma words: closes the `DDL(...)` route for those, no help against raw SQL, more rules to carry. Make every SQLite rule dialect-aware: more code, no change in outcome.
- **Trade-offs:** Replacing a trigger function and planting a future id are not refused by the guard; the first needs the owner role, the second raw SQL or COPY with `INSERT`. Both are recorded in the data-model record. Until the migration URL (#205) and the Compose roles (D11) land, the app and the migrations connect as one role, which owns the table, so in a deployment the owner-only limits are open to the app's role.
- **Evidence:** issue #195 and its PM comment; #193 (D6a); #107 (PR #217); the Deploy record decision 8 (`_docs/decisions/2026-11-13T2156Z-deploy.md`); `socboard/audit_guard.py`; `tests/test_data_audit_guard_postgres.py`.
