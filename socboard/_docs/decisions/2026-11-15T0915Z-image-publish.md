# Decision: The tested image is pushed to ghcr.io only from a push to main, by one job, tagged with the commit's time and sha

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-15, in the Compose and CI lane session: "recommendations approved", in answer to the lane's message asking for approval of the Decision record in issue #235 and of the gate mechanism) (issue #235, Deploy item D14; copied from the issue's `## Decision record` section, body hash `9a4535638c15e8320bbcf6205331bef8fe734831313df96b2875839633a2c592`, with the additions marked below).

- **Decision:** (1) The image is pushed to `ghcr.io/<owner>/socboard` only from a `push` to `main`, by a job that alone holds `packages: write`, after the other checks for that commit have succeeded, and it is the image the integration tests ran against. (2) The tag is `YYYYMMDD-HHMMSS-<7 character sha>`, with no `latest`; D20 and D22a deploy by the digest. (3) Third-party actions in that job are pinned by commit SHA.
  - (added: the gate, approved with the record) The gate is a `workflow_run` workflow, `publish.yml`, triggered when any workflow that runs on a push to `main` completes. A gate job with `actions: read` and `contents: read` lists the commit's workflow runs and decides in `scripts/publish_gate.py`: the four required workflows must have a run, and every run of the commit must be completed with `success`; otherwise it ends quietly and a later completion tries again. The rule is generic on purpose: a check added later, or the Terraform check on a commit that touched `terraform/`, is waited for without a change to the script; a test fails if a workflow that runs on a push is missing from the trigger list.
  - (added: how the image reaches the publisher) The Compose job checks the files of the image it tested (`scripts/check_image_files.py`), saves it with `docker save` and uploads it as an artifact kept one day, on a push to `main` only. The publishing job downloads that artifact, loads it, checks that its id is the id the Compose job recorded, pushes it, pulls it back by digest and compares ids. It runs no code from the repository, so the job that holds the registry token never executes a commit's scripts.
  - (added: labels) The image's `source`, `revision` and `created` labels are set at build time from two build arguments (`GIT_COMMIT`, `BUILD_DATE`), passed by `compose.yaml` and set by the Compose job, because adding a label after the test would change the image id and so break "the image that was tested".
  - (added: concurrency) The publishing job has one non-cancelling concurrency group, so a running push is never cancelled. (added: the gate counts only this commit's runs on `main` of this repository, so the same sha pushed to another branch or fork can neither hide a failure nor block a publish.)
- **Reason:** The deploy runs the image as root on the server (D20), so what may be published decides what may be deployed. A rebuilt image could differ from the tested one. A sortable, traceable tag lets the DevOps phase promote the same artifact, and `latest` would let a deploy pick up an untested image. `workflow_run` workflows run from the default branch, so a pull request or a fork cannot change the job that holds the token. The trigger has no branch filter, so a pull request's runs start the workflow and its gate job is skipped, which makes "a pull request never pushes" visible.
- **Alternatives:** Push from every branch (a branch could overwrite a tag a deploy trusts); one workflow that holds every job (a simpler gate, but it moves the four existing workflows); build in the publish job (an untested image); a personal access token (a long-lived credential, which the Deploy record forbids); tag by commit sha only (not sortable); (added) trigger on the Compose workflow only (other checks could still be running, so it would have to poll).
- **Trade-offs:** The `workflow_run` gate adds a second workflow and an API read of the other runs. The gate runs once per completing workflow on any branch (the ones that are not a push to `main` end at a skipped job), and usually one run for a commit finds everything green; if two finish together both can, and the second finds the tag already published and checks it instead of pushing (added). GitHub keeps one pending run per concurrency group, so three quick merges could replace the pending second publish and leave its commit without an image (`VERIFY:` on the first runs); the next green push publishes its own. A public package means anyone can pull the image; it holds no secret (#190's check passes on the tested image) and the repository is public. A tag from the commit time is stable on a re-run but not unique if two commits share a second (the short sha separates them). `publish.yml` cannot run before it is on `main`, so its Docker steps are checked only by reading them until the first push to `main`; the gate, the tag and the name are unit-tested. The first image the package holds is private until the human makes it public.
