# Decision: a read-only Terraform plan of the server part on same-repository pull requests, showing only counts

One file per choice that may be revisited. When it becomes stable, link to this file instead of copying it. **Status: approved** (the human, 2026-11-15, by name, as the `## Decision record` section of issue #209, D18b, at body hash `e2561dce7c004f0d07e609b480ee6ce30fe602d3903a5dae723e3f4b78b8e58a`). Only the human sets `approved`. Heavy tier: the first workflow to hold a cloud role. It applies decision 10 of the Deploy decision record (`2026-11-13T2156Z-deploy.md`) and the plan role of `2026-11-14T0928Z-ci-oidc-roles.md`. Decision, Reason, Alternatives and Trade-offs are the approved text unchanged; Evidence adds the issue and the files as built.

- **Decision:** a separate workflow `terraform-plan.yml` runs on `pull_request` only, for changes to `terraform/server/`, with workflow permissions empty and the job holding only `id-token: write` and `contents: read`; it skips fork pull requests by a job condition; it assumes the plan role with the AWS credentials action pinned by commit; it runs `init` with the bucket from a repository variable and `plan -lock=false`; it saves the plan to a temporary file and shows only the counts to add, change, replace and destroy in the job log and job summary, posting no comment and never printing the full plan; a standard-library script reads `terraform show -json` of the saved plan and fails the job on any action other than no-op, create, update or read, so a destroy or replace never passes CI. A test forbids `pull_request_target` in every workflow and allows `id-token: write` only with a `pull_request`-only trigger.
- **Reason:** the plan role trusts the `:pull_request` subject, which both `pull_request` and `pull_request_target` runs carry; only `pull_request` runs a fork's code without base-repository rights and without an OIDC token, so banning `pull_request_target` keeps forks away from the role. No comment means no write token in a job that runs code from any same-repository branch. `-lock=false` is forced by the read-only role. The human is the sole reviewer and does not read a full plan (ruling of 2026-11-14), so the full plan would add nothing but exposure in a public log; printing only counts keeps the account number and resource attributes out of it without masking. A machine check on destroy and replace catches the change a reviewer most needs to see, since the plan's detail is not read.
- **Alternatives:** add the plan to `terraform-check.yml` (one file, but that job then holds a cloud role on every Terraform change, including folders the role cannot plan); post the plan as a comment with `pull-requests: write` (easier to read, but a write token in a job any branch can change); raw `aws sts assume-role-with-web-identity` with `curl`, as in the #156 task file (no new action, but the credentials handling is hand-written); the full plan in the log with the account number masked (rejected: the sole reviewer does not read a full plan, and masking is best-effort); a `jq` filter inline in the workflow instead of a script (no new file, but its refused cases cannot be tested offline).
- **Trade-offs:** a same-repository pull request can edit the workflow and run any command with the plan role: accepted by #156 (the role is read-only and cannot read a secret value, but it can read user data and every `ec2:Describe*` result); a plan without a lock can read state while a human apply is running and show a stale result; nobody sees the detail of a change in CI, so a harmful in-place update (for example a changed security group rule on an existing resource, or new user data) passes the check and is seen only in the code diff; the check also blocks deliberate replacements, which then need the human's apply; a failed run shows only a fixed message, so every failure (a denied read, a wrong variable, a provider error) is diagnosed by the human locally with the README's plan step, at the cost of a slower fix; in exchange no Terraform or AWS error text, which can name an ARN and so the account number, reaches the public log.
- **Evidence:** issue #209; `terraform/ci-access/plan.tf` and its README section (#156); `terraform/server/backend.tf.example` (#199); the Deploy decision record, section F and decision 10; the draft in `_docs/planning/deploy-draft/wave-2-issue-drafts.md`. As built: `.github/workflows/terraform-plan.yml`, `scripts/check_plan_actions.py`, `tests/test_check_plan_actions.py`, `tests/test_terraform_plan_workflow.py`.

## Addendum, 2026-11-16: mask the plan role's unique ID (human rulings A and B)

Not part of the approved text above; it records two rulings the human made after the first run. The approved text's "without masking" and its one-job shape no longer hold.

- **Finding:** the first run (43747150371) printed the plan role's unique ID in the credentials step ("Authenticated as assumedRoleId AROA..."). `mask-aws-account-id` does not hide it. The human deleted that run's logs.
- **Ruling A:** a step before the credentials step masks the ID, read from the repository secret `AWS_PLAN_ROLE_ID` (a stored secret the job never uses is not masked, so the workflow must reference it). The plan job fails with a fixed message if the secret is empty.
- **Ruling B:** a second job, `log-check` (`needs: plan`, `if: always()` and the same-repository condition, `permissions: actions: read` only, no secret), downloads the plan job's log through the REST API after it ends and fails if it matches `AROA[A-Z0-9]+`. A step cannot read its own job's log, hence the second job. It prints only fixed pass or fail lines and fails closed when the log cannot be fetched or is empty.
- **Trade-offs:** the check detects a leak after the log is public; it does not undo it, so the human deletes that run's logs. A transient API error turns a clean run red. A same-repository pull request can edit the `log-check` job, which holds only `actions: read`.
- **Evidence:** `.github/workflows/terraform-plan.yml`, `tests/test_terraform_plan_workflow.py`; the secret `AWS_PLAN_ROLE_ID` is described in `terraform/README.md` (Outputs), with notes in the #156 and #207 task files (added 2026-11-16).

## Addendum 2, 2026-11-16: the log-check job is removed; follow-up #307

- **Finding:** in three runs at PR #263 (43777278028 at 450fbd5, 43780300200 at 342bb88, 43784106149 at 2988b71) the mask step and the credentials step passed and the plan job's log held 0 matches of `AROA[A-Z0-9]+` when counted from outside the run, so ruling A works. The `log-check` job failed in all three: the jobs listing worked, the log download failed inside the run on all 5 tries 15 s apart ("no HTTP status" in the last run); the same download works from outside the run after it ends.
- **Ruling (the human, Decision 1):** the in-run check is removed from this workflow and moved to follow-up issue #307, so #209 is not held up by the backstop. Ruling A stands. The workflow is one job again. Its last version with the job is commit 2988b71.
- **Trade-offs:** until #307, nothing checks the public log after a run; masking is best-effort and depends on the secret `AWS_PLAN_ROLE_ID` holding the current role's unique ID (a recreated role has a new one).
- **Evidence:** `.github/workflows/terraform-plan.yml`, `tests/test_terraform_plan_workflow.py`, issue #307.
