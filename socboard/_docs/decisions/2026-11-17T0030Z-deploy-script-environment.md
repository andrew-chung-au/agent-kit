# Decision: The deploy script takes the environment (dev or prod) as a second parameter and sets every per-environment value from one fixed table

One file per choice that may be revisited. **Status: approved** (the maintainer, who approved the `## Decision record` section of issue #267 on 2026-11-16: decision questions 1 to 6 and 8 at the PM's recommended options, and question 7 settled because #314 merged and the script on `main` already holds dev's data folder `/srv/socboard-data/postgres`; the approval comment is https://github.com/andrew-chung-au/socboard/issues/267#issuecomment-6933485386; the order ruling in the same issue is "build now") (issue #267; copied from the issue's `## Decision record` section, Heavy). This record adds to the D20 record, `_docs/decisions/2026-11-15T1822Z-deploy-script.md`, and to the #281 record, `_docs/decisions/2026-11-15T2301Z-deploy-script-ambient-inputs.md`, and replaces neither.

- **Decision:** (1) The document `socboard-deploy` gains a second parameter, `environment`, with `allowedPattern` `^(dev|prod)$` and default `dev`; the script takes it as a second argument, checks the whole value again with a `case`, and refuses anything else with exit 2 and one new fixed line. (2) After the check, one fixed table in the script sets every per-environment value (project, ports, gateway and trusted proxy, data folder, secret name, release and `current` folders, container and network names); nothing is read from the environment, the document or the arguments but the checked name. (3) One lock and one variable-file path cover both stacks. (4) Prod's network and project reach Compose as `STACK_PROJECT`, `STACK_NET` and `STACK_APP_PORT` in the variable file (prod only), `compose.yaml` and the deploy role's policy are unchanged. (5) A run with `dev` or no environment behaves exactly as on `main`.
- **Reason:** The deploy role may send one document, so a parameter of that document needs no policy change, and the script keeps one copy. A closed name with a fixed table keeps #281's rule: no behaviour from the environment, and no way for a caller to choose a folder, a secret or an address. One lock follows from one Docker daemon, one small server and one variable file. `compose.yaml` already takes the three variables for this (#271), so no Compose-lane change is needed. Leaving dev's path untouched keeps the first dev deploy's evidence valid for the dev branch of the same script.
- **Alternatives:** A second document `socboard-deploy-prod` (a second copy of a root script, a role policy change, and no added protection, because one role sends both). Passing values as document parameters (the caller would choose the secret and the folders; rules out #281). One lock per environment (parallel runs on 2 GiB; a changed lock path for dev). The override file carrying the prod network (Compose appends subnet entries). A separate prod role now (stronger AWS-side binding, but a second role, masking secret and apply, and a larger change than the approved record's "nothing wider"; the follow-up if wanted). A new exit code for a bad environment (a table and README change for no gain).
- **Trade-offs:** (1) The role cannot tell a dev job from a prod job; a job in the `deploy` Environment could send `environment=prod`. The controls are GitHub's reviewer gate on `deploy-prod` and the reviewed pull request (#268, trade-off 1); `VERIFY:` that Systems Manager's `SendCommand` has no IAM condition on a document parameter. (2) The script is the one place that holds both stacks' rules: a wrong row of the table (for instance the two gateways swapped) deploys one stack with the other's address. The tests assert each row by name and the swapped-gateway case is refused (exit 10). (3) One lock means a prod run waits behind a dev run. (4) Both stacks' secrets are readable by the instance role, and the script reads one of them per run by a name from its table; nothing but the table chooses the name. (5) Four static tests change shape because the document has two parameters; each is replaced by a stricter one. (6) Two apps and two Postgres servers share 2 GiB (decision record of 2026-11-16). (7) The first prod run is the human's step, so the script's prod branch is proved offline by stubs and live only by that run.
