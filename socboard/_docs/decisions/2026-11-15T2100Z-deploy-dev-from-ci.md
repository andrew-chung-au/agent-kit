# Decision: A green, published push to main deploys to dev from CI, through a separate workflow, for the newest commit only

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-16, in the Compose and CI lane session: "recommendations approved" for the five decision questions, option A on each, and "approved decisions" for the Decision record; recorded in the PM comments 6899650124 and 6899854581 on issue #238) (issue #238, Deploy item D22a; copied from the issue's `## Decision record` section, body hash `abb043c19013e9b42eae77bee3ef0cc40e1d8c77ab420f19727cf775e20eb834`, with the additions marked below). The body was edited on 2026-11-16 for two criteria, the `find` job's event and `--output json` (sha256 `e51917f83af21deeffd8ba33e6a8b043e6fabbf8b8c31430387624365ab51716`); the Decision record's text did not change.

- **Decision:** (1) A push to `main` that passes every check and is published deploys that digest to dev, through a separate workflow `deploy-dev.yml` triggered by the publish workflow, in the `deploy` Environment, with the OIDC deploy role and no stored credential. (2) The deploy sends only the document `socboard-deploy` with the digest as its one parameter, reads the result by the script's fixed lines, and then checks the public `/api/health`; a failure of either fails the job. (3) Only the newest commit deploys. (4) A passing deploy leaves the artifact `deploy-record-dev` with the digest, tag, revision and run, which the promote workflow reads. (5) The instance id and the URL are variables the human sets on the Environment.
- **Reason:** The deploy role is already limited to one document on tagged instances, so what the workflow can do is bounded by AWS, not by the workflow's text; a separate workflow keeps the publishing job (`packages: write`) and the deploying job (`id-token: write`) apart, as the publish workflow's own rule that one job holds one write permission requires. Deploying only the newest commit keeps a late older publish from moving dev backwards. A record of what dev is running is what promote and rollback need.
- **Alternatives:** A deploy job inside `publish.yml` (one file, but the publish workflow's rule "one job with a write permission" would have to change and one workflow would hold a registry write and a cloud role); reading the digest from the registry by tag (needs Docker or a registry call and trusts a tag's current target, not the digest the job verified); deploying every published digest in order (a late older run can still deploy after a newer one unless it checks, and it redeploys intermediate commits nobody needs); the GitHub Deployments API for the record (no artifact expiry, but a new permission `deployments: write` and a 140-character description to hold a digest); finding the instance by tag (the deploy role has no list or describe action).
- **Trade-offs:** The `deploy` job runs a script from the default branch while it holds the deploy role; the role can send one document and read one result, so a compromised script could send only a digest of its choosing, which the document's pattern and the script's own check bound to a well-formed digest of this repository's image (the script pulls only `ghcr.io/<owner>/socboard@<digest>`), and anyone who can change `main` can already change that. The record artifact expires after 90 days. A stale `DEPLOY_INSTANCE_ID` after an instance replacement fails the next deploy loudly until the human updates it. The deploy workflow runs, mostly doing nothing, once per publish run (about five per push); each of those costs a short job on a runner. The public health check proves the proxy, the certificate and the app, not the database.

- **(added: built)** The `deploy` job checks the two Environment variables in a step before the role is assumed, so a missing or malformed one costs no AWS call. The `find` job writes its outputs to `$GITHUB_OUTPUT` through `--output`, so its messages cannot corrupt them.
