# Decision: The observability checks run in one separate, path-filtered workflow that calls one script

One file per choice that may be revisited. **Status: proposed** (issue #340 states the decision in its body, which the maintainer approved with the `approved` label on 2026-11-16; this record is the file the issue lists. It becomes `approved` when the maintainer merges the pull request and lands the workflow.)

- **Decision:** the observability checks run in one separate, path-filtered workflow, `socboard observability`, that runs one script, `observability/ci/check.sh`. Later issues change the script, not the workflow. The workflow runs on a push or pull request that touches `observability/`, `compose.observability.yaml`, `socboard/telemetry.py`, `socboard/ingest.py`, `socboard/cases.py` or `scripts/observability_*` (and its own file), on manual dispatch and nightly. It has read-only repository access, no secret, no Environment and no cloud role.
- **Reason:** workflows are protected files, so each Docker check as its own workflow change would cost a maintainer sitting each time. A separate workflow keeps six more containers out of the Compose job, which already runs the stack tests and the browser test. The first version of the script is a walking skeleton: a collector, Tempo, Loki and Prometheus, one emitter and one query, so the three version-specific facts the plan rests on (a log line reaches Loki with its trace id as structured metadata; an exemplar survives the SDK, the collector and remote write into Prometheus; all three stores can be asked by one trace id) are run once before the lanes fan out.
- **Alternatives:** steps added to the existing Compose job (one workflow, but longer runs on every push, and every protected diff touches the CI lane's main job); a check on every pull request with no path filter (simpler triggers, but minutes on every docs change).
- **Trade-offs:** a script the workflow runs can be changed by any pull request that touches `observability/`, so the workflow's limits (a read-only token, no secret, no environment) keep it safe, not review of the script. A path filter can miss a change outside the listed paths that breaks the checks; the nightly run bounds how long that goes unseen. As a path-filtered workflow that can run on a push to `main`, it must be in the trigger list of `publish.yml` (and in `TRIGGER_LIST` of `tests/test_publish_workflow.py`); it is not in the gate's `REQUIRED` list, which holds only the workflows that run on every push. A run of it on a commit that fails holds back the publish of that commit, which is the intent (`tests/test_observability_workflow.py` shows each case). The workflow file is delivered as `observability/ci/proposed/observability.yml` until the CI lane or the maintainer lands it; landing it is a copy (its static test reads the proposed copy), plus the two edits to the publish trigger list above.
- **Evidence:** issue #340 and its decision section; the senior review relayed on 2026-11-16 (items 3, 8 and 10); `_docs/decisions/2026-11-16T0400Z-observability-backend-agent-alert.md`; `.kiro/steering/delivery-pace.md` item 1 (CI is the test loop); `tests/workflow_triggers.py` and `scripts/publish_gate.py` (how the new triggers read).
