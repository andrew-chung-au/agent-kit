# Decision: Dev and prod run as two Compose stacks on the one server; the stack being built now is dev, and prod is layered on after D20

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-16, by merging PR #265 and saying "approved" in the planning session). The human chose this on 2026-11-16 (planning session) as the easiest way to meet the course rubric's "CI runs tests, CD deploys to dev, and there's a manual deploy to production" (`_docs/planning/rubric.md`, line 61) and the spec's Phase 3 outline (`_docs/specs.md`, line 96: separate dev and prod, automatic deploy to dev, manual promotion to prod, a rollback path). The project runs for about one week, so cost is not a factor.

- **Decision:** (1) Dev and prod are two Docker Compose projects on the one server `terraform/server/` creates: each has its own containers, database folder on the data volume, stack network and pinned gateway, loopback port, secret in Secrets Manager, release folder and public hostname, served by the one host Caddy. (2) The single stack the Deploy phase is building now (#256 bootstrap, #261 gateway pin, #237 deploy script, #238 deploy from CI) **is dev**: its names, port, folder, subnet, hostname and secret do not change, and none of those issues changes scope. (3) Prod is added after D20 (#237) has run once, by separate issues that add `-prod` values on top: a second Caddy site and data folder, a per-environment parameter in the deploy script (default dev), a prod secret the instance role may read, the deploy role trusting a second GitHub Environment `deploy-prod` (dev keeps the existing `deploy`), and a manual promote workflow that deploys to prod the image digest dev is running, with rollback as a promote of the previous digest. (4) Prod deploys need the human's approval in `deploy-prod`; dev deploys automatically on a green push to `main`.
- **Reason:** It needs no second AWS account, no new Terraform part and no second server; the human's only new applies are small changes to `ci-access/` and `iam-and-budgets/` with steps the human has already run. Keeping the in-flight stack as dev means no work under way is redone or re-approved. Promotion by digest is the "build once, deploy many" rule of `_docs/planning/04_devops.md` and #235's tag scheme.
- **Alternatives:** A second AWS member account for prod (full isolation, no Terraform code change, but every part applied again and new CI roles); dev and prod in one account as two servers with environment-suffixed names (changes to `server/`, `ci-access/` and `iam-and-budgets/`, a second server); prod added now inside the in-flight issues (rework and re-approval of #256, #237 and #261 mid-build).
- **Trade-offs:** Dev and prod share a host, so a server fault, a full disk or a bad bootstrap change takes both down; acceptable for a one-week course project. Two apps and two Postgres servers on a `t3.small` (2 GiB) may be tight; `t3.medium` is an allowed size in `server/variables.tf` if needed. The instance role reads two secrets, so a compromise of the host reaches both. The snapshot schedule backs up the one data volume, which holds both databases. Each change to the bootstrap replaces the instance and so restarts both stacks. `VERIFY:` that sslip.io resolves a prefixed name such as `dev-<ip>.sslip.io` (the prod issues pick the names).
