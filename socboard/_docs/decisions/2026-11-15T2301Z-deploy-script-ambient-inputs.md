# Decision: The deploy script reads nothing of its behaviour from the environment, unsets the names it writes, and treats a failed `current` link as a failure after the swap

One file per choice that may be revisited. **Status: approved** (the human, who approved the `## Decision record` section of issue #281 as written and ruled decision questions 1 to 3 at option 1 in the Claim comment, https://github.com/andrew-chung-au/socboard/issues/281#issuecomment-6902753030) (issue #281; copied from the issue's `## Decision record` section, body hash `1053688706055be2b65a3ca3728aad7b2792c9dd0125f3973a8325e5d43dc2d0`, confirmed in the Confirm comment https://github.com/andrew-chung-au/socboard/issues/281#issuecomment-6903905826, with the decided options marked below). This record adds to the D20 record, `_docs/decisions/2026-11-15T1822Z-deploy-script.md`, and does not replace it.

- **Decided options of the decision questions** (the human chose option 1 of each, in the Claim comment above):
  1. The real script holds no test hook: `RUN_DIR`, `OPT_DIR`, `WAIT` and `POLL` are literal constants, and the tests run a rewritten copy.
  2. A failed update of the `current` link takes the existing restore path, with no new exit code and no new fixed text.
  3. The unset list is the ten names the script writes into its variable file; names that `compose.yaml` defaults and the script does not write, and `COMPOSE_*` names, are not covered.
- **Decision:** The real script holds no test hook: `RUN_DIR`, `OPT_DIR`, `WAIT` and `POLL` are literal constants, and the script reads nothing of its behaviour from the environment except what Systems Manager and the host provide (`PATH`, the instance's role). `tests/test_deploy_script.py` runs a copy of the script written to the test's folder with exactly those four assignments replaced (test paths, `1` and `0.05`), and a test asserts the copy differs from the real file in those lines only. The ten names the script writes into its variable file (the eight secret names, `STACK_IMAGE` and `STACK_PGDATA_DIR`) are unset at the start. A failed update of the `current` link is a failure after the swap and takes the existing restore path (exit 7 or 9).
- **Reason:** The script is a root script that holds every secret; whatever sets its behaviour must not be reachable from the environment of the shell that runs it. A flag read from the environment (option 2) is as ambient as the hooks it guards. Removing the hooks leaves nothing to set. Folding the link into the swap reuses the restore path, so the running image and `current` cannot disagree and no new text or exit code is added to the failure table of the D20 record.
- **Alternatives:** (1) Keep the hooks as they are: the finding stays. (2) Honour the hooks only when an environment flag such as `SOCBOARD_DEPLOY_TEST=1` is set: tests change a little, but root's environment can set the flag as easily as the hooks, so the gap stays. (3) Honour them only through a command-line argument: Systems Manager replaces only the digest parameter, so the document never passes it, but test code stays in the root script and the digest argument form changes. (4) For the link: keep the new release running and exit 7 with a new reason text ("the current-release link could not be updated"): no restore of a healthy release, but a new fixed text in the failure table (the README and the task file change) and `current` and the running image disagree.
- **Trade-offs:** Tests run a rewritten copy, so a mistake in the rewrite could hide a difference; the line-exact comparison with the real file and the static test of the real file's constants bound that. A link failure on an otherwise healthy release now costs a restore (a short outage, as any exit 7) instead of a quiet success; the cost is accepted because the previous design printed success over a wrong link. No migration is undone by the restore (D20 record, Trade-offs 3), as for every exit 7. A `BASH_ENV` set in the environment of the shell that starts the script is sourced by that outer bash before the script's first line, which no script can prevent; the re-exec stops it from reaching the real run (added, fix round 1, the human's option A). The script is started by Systems Manager with `sh` (dash on Ubuntu), so the start-up block that hands over to `/bin/bash --norc --noprofile` under an empty environment is written in POSIX sh and cannot use bash features; a static test of those lines and a CI run of the script copy with `sh` bound that, and the human's first deploy is the live check.
