# Decision: The deploy script is the content of one Systems Manager document, migrates through Compose's own services, proves the new image as a candidate, and restores the previous image on a failed swap

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-15, who approved the `## Decision record` section of issue #237 as written and ruled decision questions 1 to 7 at their recommended options: issue #237, comments 6898705331 (rulings), 6900909439 (confirm, https://github.com/andrew-chung-au/socboard/issues/237#issuecomment-6900909439) and 6898956834 (claim), https://github.com/andrew-chung-au/socboard/issues/237#issuecomment-6898956834) (issue #237, Deploy item D20; copied from the issue's `## Decision record` section, body hash `a9508b1e0efdb2198190835dff70174eaa649407b325701e98eae5152cfb4bd3`, with the decided options and the additions marked below).

- **Decided options of the decision questions** (the PM's comment on #237 asked them; the human chose the recommended option of each):
  1. **#205** (migrations with their own database URL) is closed as not planned: `migrate` already connects as the owner role through Compose, so no second variable is needed.
  2. **Where the script lives:** it is the content of a Terraform `aws_ssm_document` in `terraform/server/` (`terraform/server/socboard-deploy.sh` and `terraform/server/deploy_document.tf`), not a document made by hand and not fetched at run time.
  3. **How the host reads the secret:** with `python3` and `python3-boto3`; the script installs `python3-boto3` from Ubuntu's archive if it is missing.
  4. **Where `compose.yaml` and `compose/db_init.py` come from:** fetched from `raw.githubusercontent.com` at the revision stored in the image's own `org.opencontainers.image.revision` label.
  5. **The swap:** a candidate on `127.0.0.1:8001` first, then the swap with a short outage; host Caddy is not reloaded; any failed check after the swap restores the previous image.
  6. **Migrations:** none is undone by a restore (the rule is in Trade-offs 3); nothing enforces that a migration keeps the previous release working, and no follow-up is filed unless the human asks.
  7. **The trusted proxy address and the restart policy** are set through the Compose override file the script writes next to `compose.yaml` (`deploy.override.yaml`); `compose.yaml` is unchanged.
- **Decision:**
  1. **Delivery and running.** The script `terraform/server/socboard-deploy.sh` is the whole content of one Systems Manager document `socboard-deploy`, created by a Terraform resource in `terraform/server/` (the human applies it first; CI's apply role may update it later). The document has one parameter, `digest`, with an `allowedPattern` and a second check in the script. The script fetches nothing it executes: it fetches only `compose.yaml` and `compose/db_init.py`, as data for Compose, from the repository at the revision stored in the image's own label, and it runs only the image it pulled by digest. The human sends it with `aws ssm send-command` with their own credentials; D22a later sends it with the deploy role.
  2. **Migration.** `db-init`, `migrate` and `seed` run as Compose's own one-shot services (`run --rm --no-deps`), from the new image, before the old app is touched. `migrate` connects as the owner role and `seed` and `app` as the application role, exactly as `compose.yaml` says; the script runs no SQL and sets no database URL. #205 is not needed.
  3. **Keeping the current release serving.** Before the swap the script does everything that can fail without touching the running app: pull by digest and check the image's labels, fetch the files, pull the pinned database image, read the secret, run the three one-shot services, start the new image as a candidate on a spare loopback port and wait for it to be healthy. Only then does it swap the `app` container with `up -d --no-deps`, checks the new release (health, the full smoke check on loopback, a request through host Caddy), and starts the previous image again if any check fails. Host Caddy and its configuration are not touched, so there is no reload that could fail.
  4. **The secret to the containers.** The instance's role reads the one secret `socboard/app` (a JSON object of eight values). The script writes the values to `/run/socboard-deploy/stack-vars` (a memory file system, mode 0600, root), Compose reads that file only to fill `${NAME}` in `compose.yaml`, and each service receives only the variables `compose.yaml` names for it (`app`: the token secret, the ingest key and the application role's database URL; `seed`: the three seed passwords and that URL; `migrate`: the owner role's URL; `db-init` and `db`: the database passwords). The file is deleted when the script exits. No secret is in an argument, a log, the image, the user data, the repository, a GitHub variable or the command history.
  5. (added with the decided options) **The proxy address and the restart policy.** The script writes `deploy.override.yaml` into the release directory with `restart: unless-stopped` for `db` and `app` and `SOCBOARD_TRUSTED_PROXIES` set to the expected `10.231.77.1`, and starts Compose with both files. Right after `db` is up it reads the stack network's gateway and stops with exit 10 if it is not that address.
- **Reason:**
  1. The deploy role may send only one named document and cannot read a secret or run a generic shell (`_docs/decisions/2026-11-14T0928Z-ci-oidc-roles.md`). A fixed script inside the document is the only form that keeps that true: if the script were fetched at run time, whoever can change the fetched text would be root on the server. Terraform keeps the document under review, in the plan and in `terraform test`, and the CI apply role was already given document management for this purpose.
  2. Each service in `compose.yaml` already has its own database URL and role (decision 8 of `_docs/decisions/2026-11-13T2156Z-deploy.md`), the host has no Python environment, uv or `make` for the project (the bootstrap installs three packages), and the Compose job already proves the application role cannot disable the audit triggers. Reusing the services makes a second variable unnecessary.
  3. A failed pull, label, file, secret, migration or candidate must cost nothing. The old app cannot be stopped first, because only one container can hold port 8000, so the candidate uses another loopback port and the swap is the only moment the app is down.
  4. Compose needs the values to build the services' environments, and the environment of a service is the narrowest place for them. A memory file system keeps secrets off the disk, and Docker's own container configuration (readable only by root) is the one place they remain.
  5. (added) The proxy address and the restart policy are deployment settings, not part of the stack's local shape, so the override file keeps `compose.yaml` and its test of the proxy's fixed address unchanged. A wrong guess of the gateway would put every login in one shared bucket, so the script checks the real gateway at run time and fails the deploy instead.
- **Alternatives:**
  1. (a) The human creates the document with the AWS command line from a JSON file in `scripts/`: no Terraform-lane change, but the document is outside the plan, the CI apply role cannot update it and a changed script would be a manual step. (b) A short document that downloads the script at a commit named by a parameter: a second parameter and a root script chosen by whoever can name a commit. (c) The document fetches the script from `main`: whatever is on `main` runs as root with every secret, with no review of the deploy itself.
  2. (a) `make migrate` on the host: needs uv and the repository on the server, and runs as whatever role the host's URL names, which is #205's problem. (b) `docker run` of the image with its own variable: duplicates what `compose.yaml` defines and can drift from it.
  3. (a) Stop the old app, then start the new one, and restore on failure: simpler, but a bad image or secret then costs an outage every time. (b) Zero downtime by running both and switching Caddy's upstream: needs Caddy's admin endpoint or a restart, and a change to the Terraform-lane Caddyfile.
  4. (a) Keep a variable file on the data volume or root disk, so a person can run `docker compose` by hand: easier to operate, but a secret at rest in a place the snapshot schedule backs up (the data volume) or that survives. (b) Pass each value with `-e` on a command line: visible in the process list. (c) Docker secrets or a secret manager sidecar: another component for one server. (d) Read the secret inside the app: a code change to the app and a wider role for the app.
  5. (added) Put `restart: unless-stopped` and the proxy address in `compose.yaml` itself: a Compose-lane change and a change of `tests/test_compose.py`'s rule that the proxy address equals the proxy's own.
- **Trade-offs:**
  1. The Terraform lane's folder holds the script and its document, so this issue needs files owned by that lane and the human's approval of that diff. A change to the script is a `terraform apply` of the document. CI's apply role may manage the document (`terraform/ci-access/apply.tf`, `ManageDeployDocument`), so once D22b exists, whoever approves an `infra` apply can change what runs as root with the secret; this is the approved CI-roles design (`_docs/decisions/2026-11-14T0928Z-ci-oidc-roles.md`), stated here, not a new decision.
  2. The owner role's password is on the server during a run, and the superuser's password reaches `db` and `db-init` only (as `compose.yaml` already says). A migration that fails halfway on Postgres can leave a partial change if it is not transactional.
  3. The swap is not zero downtime: from the old container's stop to the new one's first healthy check, usually well under a minute, at most 90 seconds, then the same again for a restore. The previous release runs against the new schema for the length of a restore, and **no migration is undone**: a migration that is not backward compatible with the previous release makes the restore fail its health check (exit 9) or misbehave. Nothing in this issue enforces that rule; it is a convention until a follow-up (decision question 6).
  4. A person on the server cannot run `docker compose` by hand without the script, because no variable file stays. Operating by hand is D23's runbook (it can read the secret again).
  5. `python3-boto3` is installed by the script on the first run, so the first run needs the package mirrors (443 and 80 are open out). If that package is not on noble, the first run fails with exit 3 and the fix is a change to this script.
  6. A run killed by the Systems Manager timeout, a reboot or a lost agent can leave a candidate container or a half-done swap. The next run starts from what Docker shows (it removes the fixed-name candidate and reads the running app's image), not from a state file.
  7. The seeded `lead` password in the secret must be the password in the database for the smoke check's login; after a `set-password` the secret and the database differ and the smoke check fails until the secret is updated (D23).
  8. (added) The first deploy needs the Compose and CI lane's change that pins the stack network's gateway to `10.231.77.1` in `compose.yaml`. Without it Docker 29.1.3 gave the network the gateway `10.231.77.128` (the first address of the network's `ip_range`), measured by the maintainer on 2026-11-16, and the script's gateway check stops the run with exit 10, which is what the check is for. With the pin merged the expected address is right.
