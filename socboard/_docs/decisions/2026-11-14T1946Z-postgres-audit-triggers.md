# Decision: The Postgres audit triggers live in migration 0002, are enabled always, and refuse a truncate too

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-15, in the Postgres lane session: "approved decisions", in answer to the list of the Postgres lane's three proposed records) (issue #193, Deploy item D6a; copied from the issue's `## Decision record` section, which the human approved with the issue, body hash `058016d3d4ee690d162c310cf68419d65ede12768eeca024b80cf0c8b3856353`, and the human's answers "#193 as recommended" on 2026-11-14; notes the Engineer added are marked "(added: ...)"). Only the human sets `approved`. The rules are the Deploy record's decision 8 (`_docs/decisions/2026-11-13T2156Z-deploy.md`, approved) and are not restated here.

- **Decision:** (1) The Postgres triggers are created by a new migration `0002` that does nothing on SQLite; `0001` is not edited. (2) The four triggers are `ENABLE ALWAYS`, so setting `session_replication_role` to `replica` does not stop them. (3) The TRUNCATE trigger's fixed text is `Audit entries cannot be truncated.`, and the duplicate-id check names `public.audit_entries`.
  - (added: found by the tests) The refusals raise SQLSTATE 23000 (`integrity_constraint_violation`), so a caller gets SQLAlchemy's `IntegrityError` with the fixed text, as with SQLite's `RAISE(ABORT, ...)`; the trigger functions also pin `search_path` to `pg_catalog`.
  - (added: found by the tests) `TRUNCATE audit_entries RESTART IDENTITY` is refused to the application role by a privilege check before any trigger (resetting the id sequence needs its owner); as the owner it reaches the trigger and is refused there.
- **Reason:** (1) A Postgres database already at `0001` never re-runs it; a new revision reaches it, and `0001`'s SQLite output stays identical. (2) Decision 8 adds that triggers do not fire in `replica` mode; the documentation says that holds only for triggers in their default configuration, and `ENABLE ALWAYS` removes the bypass for a role that is later given the `SET` privilege, at no cost to the rules in decision 8. (3) Matches the three SQLite texts; a qualified name cannot be redirected by `search_path`.
- **Alternatives:** Edit `0001` (the Postgres-driver record, `_docs/decisions/2026-11-14T1120Z-postgres-driver.md`, still `proposed`, names `0002` as the fallback): one file per fresh database, but existing Postgres databases keep no triggers. Leave the triggers in default configuration (decision 8 as worded): one line less, and the `replica` bypass stays open to any role granted `SET`. Revoke `TRUNCATE` from the application role instead of a trigger: that is the Phase 3 privilege hardening decision 8 already defers.
- **Trade-offs:** SQLite databases carry revision `0002`. The owner and any superuser can still disable or drop the triggers (decision 8). `ENABLE ALWAYS` triggers also fire on a logical replication subscriber; with only inserts of new ids there, they do not interfere, and a future restore or replica that replays UPDATE or DELETE would be refused by design. Decision 8's line "triggers do not fire when `session_replication_role` is `replica`" is correct only for default-configuration triggers, so it is incomplete rather than wrong; "cannot ... run DDL" holds for objects the role does not own, and the role is also given no `CREATE`; none of these changes a rule. Until the migration-URL follow-up (#205) and the Compose roles (D11) land, the app and the migrations connect as one role, so the two-role design is shown by the tests' throwaway roles only.
