# Decision: The audit guard unwraps a lambda_stmt and refuses one it cannot read

One file per choice that may be revisited. **Status: approved** (the human, 2026-11-15: "approve descion record", recorded in the Claim comment https://github.com/andrew-chung-au/socboard/issues/214#issuecomment-6891877840; that approval also settles the PM's decision questions 1 (unwrap and refuse, fail closed) and 2 (refuse a closure-captured `None` id)) (issue #214; copied from the issue's `## Decision record` section, body hash `1c5b57eba553fb73ed94eb26696379df511a18c7f8e4d8655bb54c3933f4225b`).

- **Decision:** `refused_statement` unwraps a `lambda_stmt` to the statement it builds (the private `_resolved` attribute, in a bounded loop; covering `LambdaElement`, which includes `StatementLambdaElement`, `LinkedLambdaElement` and `DeferredLambdaElement`, and `NullLambdaStatement`, which `.spoil()` returns) and applies every existing rule to that statement; a lambda that cannot be unwrapped is refused. The id rule, the on-conflict and `REPLACE` rule, the `sqlite_sequence` rule and the DDL rules then hold for lambdas without a lambda-specific list. A closure-captured `None` id is refused like a caller's `bindparam` (the module's existing cost); a literal `id=None` and an omitted id pass.
- **Reason:** The audit trail is append-only, the database cannot refuse a new explicit id on SQLite (and on Postgres checks reused ids only), and the guard is the only layer for the id rule (#99). The data-model record prefers enforcement to recorded gaps for this trail, and its Reason already names `lambda_stmt` as a form that got past an application-layer guard. The unwrapped statement is an ordinary `Insert`, so one change covers the id rule, the sequence rule and the upsert rules for a connection, a Session and execute parameters. Fail-closed costs nothing because `socboard/` has no `lambda_stmt`.
- **Alternatives:** (1) Record `lambda_stmt` as an open limit in the data-model record, no code: honest, but leaves a known one-line route to a permanent `append_audit` failure on SQLite, and the sqlite_sequence write. (2) Refuse every `StatementLambdaElement` outright (no unwrap): simplest, no private attribute, and nothing in `socboard/` uses one, but it blocks harmless lambda SELECTs and later application code that adopts `lambda_stmt` for caching, and a test would still need the unwrap to prove the lambda INSERT without an id works. (3) Ask SQLAlchemy for a public accessor: there is none for the built statement of a `StatementLambdaElement`; `_resolved` is private. (4) Compile the lambda to inspect the SQL: rejected by #107 (the guard no longer compiles).
- **Trade-offs:** Reads a private SQLAlchemy attribute (`_resolved`), so an upgrade can break it; fail-closed plus the canary test make that visible and safe (every lambda refused until fixed). A closure-captured `None` id is refused. Not covered, as before: raw SQL, and a custom wrapper that is neither an `Insert`/`Update`/`Delete`/DDL nor a lambda. On Postgres the same unwrap applies (no dialect is involved); the database there still checks reused ids only.
