# Decision: the server is one Ubuntu instance in the default VPC with an Elastic IP, a security group for 80 and 443 only and a protected encrypted data volume, checked offline by `terraform test`

One file per choice that may be revisited. **Status: approved** by the human on 2026-11-14, as the `## Decision record` section of issue #199 (D17b) at body hash `a70825ab7f62db0531a917c7021125ec42fabfe5ea319480e43a2841e3527561`. It is added as `approved`, not as `proposed` as the issue's Constraints line says, because the human approved that section by name in the orchestrator session on 2026-11-14, before the Engineer started (claim comment https://github.com/andrew-chung-au/socboard/issues/199#issuecomment-6881621329). Heavy tier: it sets the public server's network exposure and the boundary between containers and the instance's credentials, and changes a CI workflow. It applies decisions 1, 4, 6 and 10 of the Deploy decision record (`2026-11-13T2156Z-deploy.md`) and fits #156 and #162 as written. Every AWS detail is unchecked until the human's first apply (`VERIFY:` comments in `terraform/server/*.tf`).

- **Decision:** `terraform/server/` makes one Ubuntu 24.04 LTS x86_64 instance (image from an `aws_ami` lookup, with later image changes ignored), in the default VPC, with no key pair, metadata tokens required at hop limit 1, the instance profile `socboard-instance` named as a fixed value, an Elastic IP, a security group allowing TCP 80 and 443 in and TCP 80 and 443 out, and a separate encrypted gp3 data volume protected by `prevent_destroy`. Tags `project=socboard` go on the instance, data volume, security group and Elastic IP in the create call; the root volume stays untagged. Instance type and volume sizes are validated variables with committed defaults. The limits are checked offline by `terraform test` with a mock provider in the existing check workflow.
- **Reason:** #156's roles allow `ec2:DescribeImages` but not `ssm:GetParameter`, so an AMI lookup works and a Parameter Store lookup does not; ignoring image changes keeps a new upstream image from replacing the server and its attachment on an ordinary apply. Ubuntu has packaged Docker, Compose and Caddy repositories and the Systems Manager agent preinstalled, which keeps D17c small. x86_64 matches the single-architecture image of D10. The default VPC is used because the apply role cannot create network resources. `prevent_destroy` makes an accidental replacement of the data volume fail instead of deleting the database between snapshots. Offline tests turn the refused cases into CI results, since nobody can run Terraform against AWS before D19.
- **Alternatives:** Amazon Linux 2023 (AWS-maintained, but no packaged Compose plugin or Caddy, so D17c downloads binaries); a pinned AMI id committed as a variable default (fully reproducible, but the Engineer cannot look one up and every patch is a manual edit); the public Parameter Store image id (needs `ssm:GetParameter` added to #156's plan and apply roles); unrestricted egress (fewer surprises at first apply, wider reach for a compromised container); Graviton `t4g` (cheaper, but needs a multi-architecture image, out of scope in D10); review-only checks instead of `terraform test` (no workflow change, but the refused cases are first seen at the human's apply).
- **Trade-offs:** with image changes ignored, the base image is patched only by the host's own updates (D17c) or a deliberate replacement; `prevent_destroy` means teardown needs one manual edit; restricted egress may block something the first apply finds (`VERIFY:`); mock-provider tests check the plan's shape, not AWS behaviour, so every `VERIFY:` item is still settled at D19; trusting Canonical's owner id is a supply-chain dependency on a public publisher.
