# Responder security limits (#244, #260)

Status: written 2026-10-27 for the pre-drill hardening of the real runner (#244, follow-up to #221), and extended the same day for the `cli` runtime (#260). The `cli` runtime then ran live in the owner's on-call drill on 2026-10-28; the `sdk` runtime has never been run against a live session.

There are two real-mode runtimes (`RESPONDER_RUNTIME`). **`cli` (the default, #260)** is described first; **`sdk` (#221)** is the Agent SDK session that needs `ANTHROPIC_API_KEY`, and everything from "The tool policy is a guardrail" on describes it unless a sentence says otherwise. The SDK runtime stays until a later cleanup (the drill has now been recorded).

## The `cli` runtime (#260): what bounds the agent now

The agent is a headless `claude -p` on the owner's own Claude login. It **only commits locally**. The runner pushes and opens the pull request. Compared with the SDK runtime this removes the largest exposure: **no GitHub token and no API key is in the agent's environment**, so code the agent runs cannot read a token that can push.

What bounds it, in the order it acts:

1. **No push credential in the agent.** The CLI's environment is built from scratch (`envscrub.cli_env`): allowlisted system names, `HOME`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, the run marker and a git identity. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, `RESPONDER_*` and `GIT_CONFIG_*` are absent (a test plants each and asserts the fake CLI never sees it). The runner hands the git token to its own `git push` call only; it is in no variable the runner sets for the agent. That is all this item claims: the token still lives in the responder's own process and settings, and code the agent runs is the same operating-system user, so it may be able to read it from there (for example `/proc/<pid>/environ` of the responder, or a file on disk). That was not tested, and the token's scope (item 4) is what bounds the damage.
2. **The allow and deny list.** Generated from `policy.py` (`cli_rules.py`): edits in the writable roots, `make backend-test|responder-test|test`, `git status|diff|log`, `git add <path under a writable root>` and `git commit -m "<message>"`; `git push`, `gh`, `curl`, web tools, `make install`, `uv`, `npm`, `pytest` and protected paths denied; `--permission-mode dontAsk` denies the rest. This is a guardrail for a confused agent. What it **guarantees**, as modelled by `cli_rules.evaluate` and checked by one test per refused case (`test_cli_rules.py`; the model, not the real CLI, is what the tests run against, `VERIFY:`):
   * `git status|diff|log|add|commit`: no argument containing `$`, `{` or `}` (shell expansion: `--${u}output=x` runs as `--output=x` when `u` is unset, and `{a,b}` is brace expansion, so the denials below would not see the flag; QA round 3 found `--output` written outside the checkout this way). `$(...)` and backticks are not matched by that pattern; the model checks the inner command as a subcommand. `ToolPolicy` refuses the same characters as shell metacharacters.
   * `git status|diff|log`: no argument containing a quote or backslash; no `--output`, `--no-index`, `--ext-diff`, `--textconv`, `--orderfile` or `-O` and no unambiguous or ambiguous prefix of them of three characters or more as a whole argument (QA found `--output=<path>` wrote outside the checkout).
   * `git add` (paths): only a path beginning with a writable root; no flag (so no `--`, `-A`, `-f`), no `.`, `..`, absolute path, quote, backslash or `*` (a tab is no longer refused by a rule, see below); no `.env*`, `Dockerfile*`, `compose*.yaml|yml`, Terraform suffix, lockfile, protected directory name or `responder/vt_responder/` in the text.
   * `git commit`: allowed in exactly one shape, by a positive match rather than a list of bad flags: `git commit -m "<text>"` or `git commit -m '<text>'`, with the start (`-m` and an opening quote) and the end (the closing quote) fixed by the allow rule and `<text>` made one shell word by the deny rules: no third quote of the same kind (so at most two apostrophes in a double-quoted message), no backslash, `$`, `{`, `}`, no leading `-`, no backtick and none of `& ( ) ; < > |`. So `-m "x"z "-a"` and `-m "x"-m "-a"` (QA round 5) are refused, as is every second argument; a message such as `Don't drop failed jobs` is allowed. A rule is a glob and cannot state a character set; the stricter tokenising check is `ToolPolicy`, and `test_cli_rules_differential.py` asserts over 6 000 generated commands (fixed seed) that the rules never allow a `git add` or `git commit` that `ToolPolicy` refuses, apart from trimming leading and trailing space, tab and newline. `prompt.py` tells the agent.
   * `git add`: one path per command (a second argument is refused), so the writable-root check applies to the only path.
   * `git status|diff|log|add|commit`, tab / vertical tab / form feed / carriage return: **no longer refused by a rule** (changed 2026-10-28). The owner's probe with the real claude 2.1.311 showed that the CLI reads a control character inside a rule PATTERN as a space, so `Bash(git commit *<TAB>*)` acted as `git commit * *` and denied every commit with a space in its message (and the same patterns would over-deny two-argument `git diff` / `git add`). Those patterns were removed (`test_no_rule_pattern_contains_a_control_whitespace_character`). What is lost, stated without overclaiming: for `git commit`, a tab outside the quotes after the message is still stopped by the positive shape (the allow rule needs `-m "` at the start and `"` at the end) and the third-quote denies, so this is expected to hold but a tab in the COMMAND text was not tested against the real CLI; a tab inside the quotes is part of the message word. For `git add`, `Bash(git add * *)` catches a second path after a SPACE; whether the CLI normalises a real tab in the command before matching is unverified (`VERIFY:`), so `git add backend/x<TAB>README.md` may match the `backend/*` allow and stage a second path. The backstop is the runner's diff gate (`publisher.py`), which refuses any changed path outside the writable roots, protected paths, lockfiles and odd names. For `git status|diff|log` the flag denies (`--output`, `--no-index`, ...) never depended on a tab, but a tab before a flag may hide it from those patterns if the CLI matches raw text; residual risk, limited by these commands being read-only apart from `--output`, which writes only if the checkout-bounded process can. Newline is a command separator and is checked as one. `ToolPolicy` (not used by the CLI) is unchanged and still refuses these forms.

   What it does **not** guarantee, left to the diff gate (item 3) or to nothing: `~` and the `*` glob in `git status|diff|log` arguments (not refused; they read inside the checkout, and a directory the agent's own code creates is needed to turn them into a flag); the `?`, `[` and `]` glob characters in `git add` paths (not refused by the rules; `ToolPolicy` refuses them; the gate refuses a protected result); protected names in another case (`DOCKERFILE`, `.GitHub`: the rules are case-sensitive, the gate is not); a path that is a symlink; anything the agent's own code does (a test that `make test` runs); and any difference between `evaluate` and the real CLI, whose matching of quotes, backslash escapes (`\*`, `\\` in a rule) and abbreviations is unverified. If the real CLI matches differently, a form listed above may be allowed there. `ToolPolicy` (the `sdk` runtime's check) is stricter than the rules in most of these, and looser in a few (the SDK agent may push its own branch). What a CLI rule cannot express is listed in `_docs/responder-cli-runtime.md`.
3. **The runner-side diff gate (`publisher.py`).** Independent of what the CLI enforced, before any push: the head descends from the cloned head, no merge commit, at most `RESPONDER_MAX_COMMITS` commits, every file the head's tree changes relative to the clone is inside the writable roots and off `.github/`, infrastructure, `.env*`, lockfiles and `responder/vt_responder/`, with a path of at most 200 characters from `A-Za-z0-9._/+=,~-` (the paths go into the pull request body), no symlink, submodule (a gitlink, mode 160000), type change, new executable or mode change. The changed paths come from `git diff --raw` between the two commits and are checked as text, with no lookup of where the working tree would resolve them (a directory swapped for a symlink after the commit does not change the verdict; tested). That call is not independent of the working tree in every respect: git reads `.gitmodules` from the working tree to decide whether to list a submodule, so an untracked `.gitmodules` with `ignore = all` hid a committed gitlink (found by QA, round 3). The call now passes `--ignore-submodules=none`, which is tested against real git; any other working-tree input to that call has not been examined (R2 below). Git objects are read without `refs/replace`. **How the push is kept on the right repository:** every runner git call (gate, squash, push) sets `GIT_DIR` and `GIT_COMMON_DIR` to the checkout's own `.git`, ignores the global and system git config (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`; the runner's clone does too), switches hooks and fsmonitor off, and pushes to an explicit URL. The run is refused (`git_dir_unexpected`) if `.git` is a symlink or holds `commondir`, `gitdir`, `config.worktree`, `info/grafts` or alternates, and (`git_config_modified`) if `.git/config` differs from its digest after the clone, checked at the start and again right before the push (a plant of `commondir` pointing at a copy of `.git` with a `url.insteadOf` was found by QA to redirect the push while the digest matched; tests now cover it). **What is pushed is ONE commit the runner builds** (the checked tree, parent the cloned head, the runner's message), so the agent's own commits, and anything it added and removed along the way, never leave the machine. A refusal is a failed run, nothing is pushed.

   What this guarantees: the commit that is pushed changes only allowed paths, as plain files, relative to the commit that was cloned. What it does **not** guarantee: it reads the agent's repository, which the agent's code can write to (R2: every read the gate makes, objects, refs and config, comes from a directory the agent's code could change; the refusals above are a list of things that were thought of, and five bypasses were found by QA and fixed one by one), and **R1:** a process that survived the group and marker kill (a child started with `env -i` or `setsid`; the kill is best effort) could edit `.git/config` in the short window between the re-check and the push, and redirect it; nothing here closes that window. It also says nothing about what the code in the pushed files does: an allowed file can still contain harmful code, which is what the human review and `protect-main` are for. It does not depend on the CLI's own permission rules, but it does depend on `git` and on the repository state being read honestly.
4. **The token's scope (#222) and `protect-main`.** The runner's token is a fine-grained, repository-only token and `main` is protected, so even a bug in the gate cannot change `main` without a reviewed merge. The runner pushes only `<sha>:refs/heads/responder/<fp>` and never forces.
5. **Run limits.** A turn limit (`--max-turns`, `RESPONDER_MAX_TURNS`) and a wall-clock limit. **There is no dollar cap on a plan** (`RESPONDER_MAX_BUDGET_USD` applies to the `sdk` runtime only); a run that hits the plan's usage limit ends as a failed run. The CLI runs in its own process group, killed as a group on the time limit, and again by the per-run marker before the checkout is removed.
6. **Branch and pull-request checks.** Cleanup deletes only a `responder/<fp>` branch this run created; the opened pull request is read back and must be this run's (S4). The pull request body is composed by the runner; the agent's summary is redacted, shortened to 300 characters and fenced.

What does **not** bound it (known limits of the `cli` runtime):

* **The Claude login is readable by code the agent runs.** `HOME` is the owner's real `HOME` and the CLI needs `~/.claude/.credentials.json` (or `CLAUDE_CONFIG_DIR`). Any process the agent starts (a test, a `conftest.py`, a package script run by `make test`) runs as the same user and can read that file, and so can the files of anything else under `HOME` (`~/.netrc`, `~/.aws`, `~/.config/gh`, SSH keys). The environment scrub covers variables only. A stolen login can use the owner's plan, which is the cost of "no API key" and is accepted for the supervised drill (#260 decision 3, as B13). Run the drill as an account whose `HOME` holds nothing else the agent should not reach, ideally a throwaway one.
* **The agent's code has network.** Nothing restricts egress; the proxy and CA variables are allowlisted because the CLI needs the network. The container with limited egress (below) is still not built.
* **Plan usage, not dollars.** A confused or looping agent spends the owner's plan allowance (bounded by the turn and time limits) rather than money. The first run should start with a fresh allowance.
* **The runner's own git calls read the checkout** the agent wrote to. The gate switches off hooks and fsmonitor, disables external diff drivers, names `GIT_DIR` and `GIT_COMMON_DIR` and refuses a changed `.git/config` and the indirection files listed in item 3, but it is not a defence against every way a repository can make git run code; the install step (`make install` with network) and the tests the agent writes already run arbitrary code in the same checkout.
* **The policy modules are protected from the agent, not from a human merge.** The gate refuses a diff touching `responder/vt_responder/`, so an agent cannot weaken the gate through a pull request it opens; a person can still change it.

Owner decisions for this runtime (#260, 2026-10-27, "go"): the `cli` runtime is added beside the SDK one; the runner pushes and opens the PR; the CLI runs on the real login with the API-key variables removed, and the login files under `HOME` being readable by the agent's code is accepted for the supervised drill; the owner runs this on their own plan for their own coursework (the agent that wrote the issue did not read Anthropic's terms for it). Like B13, this acceptance is scoped to the **supervised, recorded drill** and must be revisited before any unattended or production use. These decisions supersede "Owner decision 2" below **for the `cli` runtime** only.

## The tool policy is a guardrail, not a sandbox

`responder/vt_responder/policy.py` stops a **confused** agent from doing the wrong thing by accident: writing to `.github/`, pushing to `main`, running an unlisted command. It does **not** contain an agent that has been prompt-injected or is otherwise hostile. The policy allows the agent to edit code and tests under `backend`, `tests`, `frontend` and `responder` and to run `make backend-test`, `make responder-test` and `make test`. Code the agent writes into a test, a `conftest.py` or `frontend/package.json` then runs as an ordinary child of the agent, with the agent's environment and network. The policy cannot see inside it. No document in this repository should say otherwise.

## What actually bounds a hostile agent

1. **Token scope (#222).** The responder's GitHub token is a fine-grained, repository-only token. #222 showed that a push to `main` with it is rejected.
2. **`protect-main`.** The repository ruleset rejects direct pushes to `main`, so a stolen token still cannot change `main` without a reviewed merge.
3. **The environment scrub (#244, B1).** `build_options` overrides every inherited variable that is not on a short allowlist with an empty string, so `RESPONDER_API_TOKEN`, `RESPONDER_WEBHOOK_SECRET`, `RESPONDER_GITHUB_TOKEN`, database, mail and cloud credentials are not visible to the agent or its children. The SDK builds the CLI environment as `{**os.environ, **options.env}` (`claude_agent_sdk/_internal/transport/subprocess_cli.py`, 0.2.174, read in the installed package), so it can override a variable but not remove it. The dependency install the runner does before the session gets only the allowlisted names.
4. **Run limits.** Turn limit, wall-clock limit, a spend cap (`RESPONDER_MAX_BUDGET_USD`, default 3.0, passed as `max_budget_usd`, which the installed SDK turns into `--max-budget-usd`), and the agent's processes are killed (by a per-run marker in their environment) before the checkout is removed and the branch is cleaned up. The kill is best effort: Linux `/proc` only, and a child that starts with a cleaned environment (`env -i`) is not found.
5. **Branch and pull-request checks.** Cleanup deletes only a `responder/<fp>` branch this run created. A reported pull request is accepted only if the REST API shows its head is `responder/<fp>` in the configured repository.

## What the scrub does not hide (known limit)

- `ANTHROPIC_API_KEY` must reach the CLI, and every Bash child inherits the CLI's environment. Code the agent runs can read it.
- `GH_TOKEN` and the `GIT_CONFIG_*` variables (the token, base64) are there because the policy lets the agent run `git push` and `gh pr create` itself. The SDK gives no way to set a variable for one Bash command only. So the git and `gh` credential is visible to code the agent runs. It is bounded only by items 1 and 2: the token can push `responder/*` branches and open pull requests in this one repository, and nothing else.
- Proxy and CA variables are on the allowlist because the CLI needs the network; a proxy URL can carry credentials.
- The scrub covers environment variables only, not files. Credentials stored under the responder's `HOME` (for example `~/.netrc`, `~/.aws`, `~/.config/gh`) are readable by code the agent runs. Run the drill on a host or account where those files hold nothing the agent should not reach, ideally a throwaway `HOME`.
- `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is a name inside the bundled CLI binary. Its error messages say it needs bubblewrap and a sandbox setup. It was not tried and nothing relies on it.

The narrowest change that would hide the git credential from the agent's children is to have the runner, not the agent, do `git push` and open the pull request (the agent would commit locally and report). That changes the agent contract and the policy; it is not built. The owner has decided against it for the drill (decision 2 below).

## Owner decision B13: accept the residual risk for the drill (2026-10-27)

The owner decided to **accept the residual risk** and not run the drill in a container with limited egress. The limits for the first live run are the environment scrub above, the repository-only fine-grained token (#222), and `protect-main`.

This acceptance is scoped to the **supervised, recorded drill on a throwaway demo defect** (task 39). It must be **revisited before any unattended or production use**: the revisit is to run the responder in a container whose network egress is limited to the Anthropic API and GitHub, which would also cover the Anthropic key and git token visibility described above. That container is not built and is out of scope for #244.

## Owner decision 2: the agent keeps `git push` and `gh pr create` for the drill (2026-10-27)

(Superseded for the `cli` runtime by #260, above: there the runner pushes and the agent holds no git credential. It still describes the `sdk` runtime.)

The owner decided to **keep it as is** for the drill: the agent runs `git push` and `gh pr create` itself through its Bash tool, and the runner does not take them over (#244 comment 6431746364). So the git credential and the Anthropic key stay visible to code the agent runs, as described under "What the scrub does not hide". The limits are the same as for B13: the repository-only fine-grained token (#222), `protect-main`, and the environment scrub for everything else.

This is scoped to the **supervised, recorded drill** (task 39). It must be **revisited before any unattended or production use**, together with the container option above: have the runner push and open the pull request while the agent only commits and reports, which would hide the git credential from the agent's children at the cost of changing the agent contract and the policy.
